# Tool Calling Loop：沿着一次 500 找到出错代码

同事发来一句话：“订单查不了了，帮忙看看。”附件只有一个请求：

```text
GET /orders/order_404
HTTP 500
```

500 说的是服务器处理请求时出了错。至于是数据库断了、字段缺了，还是哪行代码写错了，它没说。报警器响得再卖力，也不会替人查案。

我们想做一个只读排查助手：接过请求，查日志，读相关代码，指出哪里出错、为什么错，再给出修复建议。先不让它动手改。值班时已经有一个故障了，暂时不需要第二个。

![500 发出警报，小黑从抽屉里取出日志和代码查证据。](assets/tool-calling-loop-illustrations/01-evidence.png)

先看一次排查会怎样发生。配套程序里，订单服务、HTTP 请求、错误日志和文件读取都是真的；**模型由预设规则替身代替**，不用配置 Key。这样可以重复观察工具怎样被调用、结果怎样送回来。它还不能证明真实模型会自己找到原因。

在本书仓库目录运行下面这条命令。不运行也没关系，关键代码和结果都在下面。

```bash
python -B experiments/reading-pilot/demo.py
```

`-B` 只是不生成 Python 字节码缓存文件。程序会临时启动一个本机服务，发出请求，再关闭服务。终端先出现：

```text
模型：预设替身（不调用真实模型，不验证模型诊断能力）
HTTP: GET /orders/order_404 -> 500
响应: {"error": "internal_server_error"}
```

接着，替身提出第一个请求：读 `server.log`。真实模型也可以返回这样的工具申请，通常叫 **Tool Call**。申请里要说清两件事：用哪个工具，以及给它什么参数。

```python
tool_name = "read_file"
arguments = {"path": "server.log"}
```

上面是申请内容的简化表示，还没有发生文件读取。就像工单上写了“请查日志”，日志不会自己走过来。

宿主程序检查申请，再执行 `read_file`。本例只允许读日志和订单源码；申请写文件、运行 Shell 或读取其他路径都会被拒绝。这里的限制由执行入口检查，不能只在提示词里写“请自觉”。

文件读到了。下面是实际日志的摘录，省略了完整目录和 HTTP 包装代码：

```text
GET /orders/order_404 -> 500
  File ".../order_service.py", line 10, in get_order
    return {"order_id": order_id, "total": order["total"]}
TypeError: 'NoneType' object is not subscriptable
```

这段读取结果叫 **Tool Result**。程序把它加入对话，再交给模型。到这一步，模型才拿到了文件中的证据。前面的工具申请只表达“想看什么”，不能代替实际内容。

日志已经把范围缩到了 `get_order` 的第 10 行。再申请读取订单源码，返回的核心代码只有这些：

```python
ORDERS = {
    "order_001": {"total": 128},
}


def get_order(order_id):
    order = ORDERS.get(order_id)
    return {"order_id": order_id, "total": order["total"]}
```

`ORDERS` 是一个字典，可以当成按订单编号查资料的小柜子。柜子里只有 `order_001`。`ORDERS.get(order_id)` 的意思是“查一下这个编号”；找不到时，它返回 `None`，表示没有这个值。

问题就在下一行：程序没有检查是否找到订单，直接用 `order["total"]` 取金额。现在 `order` 是 `None`，已经不是那份包含金额的订单资料了，当然取不出 `total`。日志里绕口的英文，说的就是这件事。

把两份证据接起来，才有一条完整解释：

```text
请求 order_404
-> 字典里没有这个订单
-> get 返回 None
-> 代码仍然读取 order["total"]
-> Python 抛出 TypeError，接口返回 500
```

因此，本例的建议是：遇到不存在的订单，走“未找到”的处理分支，让接口返回 404；已有订单仍应返回 200 和正确金额。只读助手到此交付建议，代码并没有被修复。

现在回头看，为什么排查需要一个 **Tool Calling Loop（工具调用循环）**？因为下一步需要什么信息，要等上一步的结果回来才能决定。日志不够，就读源码；源码也对不上，就应该继续找证据或说明暂时无法判断。

```text
用户提出排查请求
-> 模型申请读日志 -> 程序读取 -> 把日志交回模型
-> 模型申请读源码 -> 程序读取 -> 把源码交回模型
-> 模型给出解释和建议
```

本例走了两次工具调用，模型侧响应了三次：申请读日志、申请读源码、给出结论。替身按预设规则完成这三次响应；接入真实模型时，才由模型根据收到的证据选择下一步。负责执行工具、回传结果和推动循环的宿主程序，就是 **Harness**。

这里也有个值得保留的疑问：既然检查步骤固定，直接写脚本不就行了？对，这个已知故障用普通脚本就能查。样例把故障缩小，是为了看清循环如何工作。真实任务中，错误位置和需要的工具可能每次不同，才值得验证模型能否帮忙选择；不能拿替身跑通冒充模型会排障。

先改一个输入，看看结论会不会跟着变。把命令末尾加上已有订单的编号：

```bash
python -B experiments/reading-pilot/demo.py --order-id order_001
```

这次输出的关键几行是：

```text
HTTP: GET /orders/order_001 -> 200
响应: {"order_id": "order_001", "total": 128}
Tool: read_file server.log
本次请求返回 200，未复现 500；不能据此声称缺陷已修复。
```

这次只读了一份日志，没有再读源码。订单能找到，取金额就成功了。原来的缺陷仍在：换回 `order_404`，500 还会回来。

读完后，试着不用术语讲给同事听：“程序先查了什么，拿到什么才查下一步，最后凭什么这样判断？”卡住时直接翻回上面的流程，不必背定义。能把这次排查讲顺，比记住 Loop 的英文更有用。
