# 第 0 课：Agent 工程史——从工具循环到可靠运行时

2023 年 3 月，Auto-GPT 从一份目标与工具设想的 Prompt，发展出连续执行命令的原型。早期代码让模型选择下一步，再停下来等待人工授权。[1]

名字里写着 Auto，执行前还得有人敲回车。在这个原型里，模型选择动作与程序允许动作发生，已经是两件事。

这一篇是选读地图，聚焦大语言模型参与后的几个工程转折：模型获得了什么能力，运行它的程序又需要承担什么工作。先理解这些变化，后面的工具、状态、权限与验收就不再只是一串术语。

## 1. 2022～2023：Tool Use 与结构化调用

2022 年的 **ReAct** 把推理、行动和观察交替组织起来。模型选择一个动作，取得外部结果，再调整下一步，而不是只凭最初输入一路生成答案。[2]

2023 年的 **Toolformer** 研究另一个问题：怎样通过训练，让模型学会何时调用哪个 API、传什么参数，以及怎样使用返回结果。[3]

```text
ReAct：边行动、边观察、边调整的交互方式
Toolformer：让模型学会使用工具的训练方法
```

两项工作都涉及工具使用，但没有替应用定义完整的权限、持久状态和故障恢复系统。模型知道该查什么，程序仍要真的去查。

Auto-GPT 的早期循环把连续选择动作落到了代码里。最早提交只有 Prompt，不能当成已经实现的运行时；后续循环才包含命令执行、逐步授权和结果回传。[1]

2023 年 6 月，OpenAI 发布 **Function Calling**：开发者描述函数，模型返回结构化的名称与参数，应用执行后再回传结果。[4] 相比从普通文字里猜“它是不是想调用工具”，程序获得了更明确的调用申请。

调用结构明确了，责任没有消失。参数是否合适、动作是否获准、结果怎样保存，仍由应用处理。本书第 1～3 课拆开的，正是模型提出动作与程序执行动作之间的这段过程。

## 2. 2023～2024：Benchmark 与操作界面

Agent 能修改仓库以后，一句“修复完成”不够用了。补丁有没有解决问题、有没有破坏旧行为，需要实际检查。

2023 年出现的 **SWE-bench** 把真实仓库问题整理成评测任务：给出代码和 Issue，要求系统生成修复，再检查结果。[5]

2024 年的 **SWE-agent** 则研究模型怎样操作仓库。导航、编辑、运行测试，以及错误怎样返回，都会影响它接下来能做什么。这套交互界面被称为 **Agent-Computer Interface（Agent 与计算机的交互界面）**。[6]

```text
SWE-bench：用什么任务检查能力，相当于试卷与验收规则
SWE-agent：执行仓库任务的 Agent 系统，相当于参加考试的系统
```

同一个模型，拿到不同工具和反馈，表现可能不同。工具只返回“失败”，与返回出错行、退出码和相关上下文，为下一步判断提供的条件差很多。

这让模型之外的工程工作变得可检验：接口是否好用，反馈是否足够，产物是否合格。后面的 Evaluation 与 Workflow 会继续用实际结果判断改动，而不是听 Agent 自己宣布成功。

## 3. 2023～2024：Context 管理与持久化

任务持续推进，会留下越来越多的历史。记录可以一直保存，模型每次能接收的输入却有限。

2023 年的 **MemGPT** 借鉴分层内存，让系统在有限 Context 与外部存储之间管理信息。[7] 它处理的是信息怎样保存、何时取回；不是要求每次把全部历史重新交给模型。

长任务还有另一种中断：等待用户、遇到错误，或者程序退出后要继续。2024 年 LangGraph v0.2 的 **Checkpointer** 保存步骤状态，用于继续会话、错误恢复和人工介入。[8]

这两类工作回答不同的问题：

```text
Context 管理：本轮让模型看到哪些信息？
状态持久化：程序从哪个已保存状态继续？
```

保存状态也不能替外部世界作证。假设邮件已发出，程序却在记录成功前崩溃，恢复点只说明最后存到了哪里，不能证明邮件没发，更不能据此再发一次。

因此，本书分开讲会话记录、模型输入和执行账本：记录过去，选择输入，再核对动作结果。它们可以协作，但“状态已恢复”不能包办所有判断。

## 4. 2024～2025：MCP 与 A2A 的协议连接

当同一份工具或数据要接入多个应用，每个应用各写一套连接代码，维护工作就会重复。

2024 年发布的 **MCP** 提供共同协议，让 AI 应用连接工具和数据等外部能力。[9] 2025 年发布的 **A2A** 则面向不同 Agent 系统之间的协作，支持发现能力、交换消息与处理任务。[10]

```text
应用接入外部工具和数据：MCP
不同 Agent 系统之间协作：A2A
```

两者可以配合。一个 Agent 系统通过 A2A 接任务，内部仍可能用 MCP 连接工具。连接成功只说明通道可用，是否应该执行、权限如何限制、结果怎样保存，仍需应用决定。

这里讲的是协议解决的连接问题，不展开后来版本的字段和握手变化。最小 Agent 也不必先接入这两套协议；先有跨系统连接的需要，再选择相应接口。

## 5. 工程责任：把历史问题接回本书

这些工作并没有按统一路线逐个替代。工具使用、状态管理与评测曾同时发展；下面是本书按工程问题整理的关系，不是某个框架的升级清单。

| 能力扩大以后 | 程序需要回答什么 | 本书对应内容 |
| --- | --- | --- |
| 模型申请工具 | 谁检查、执行并回传结果？ | 第 1～3 课：Agent、Runtime、Tool Calling Loop |
| 会话持续变长 | 历史怎样保存，本轮给模型什么？ | 第 4～5 课：Session、Checkpoint、Context |
| 工具改变外部世界 | 回执丢失能否重做，最多能影响什么？ | 第 6～7 课：Ledger、幂等、权限与 Sandbox |
| 系统持续运行和改动 | 失败在哪里，旧能力有没有退步？ | 第 8～9 课：Trace、Evaluation |
| 任务需要返工或等待 | 谁接着做，何时继续、何时停止？ | 第 10 课：Workflow 与编排 |

不少做法来自已有的 API、数据库、安全与测试实践。模型能生成动作以后，这些工作仍要有人落实；给系统起一个 Agent 的名字，并不会替它补上事务和权限。

以后看到一个新框架，我会先查它解决了表里的哪个问题，再看相关限制与验证结果。会调用工具是一项能力，不是其余工程工作的证明。

本书从一个只读排查助手开始，用代码和故障实验逐项解释这些机制。第 1 课先回答更早的问题：眼前这个任务，究竟需不需要 Agent？
