## 改写前的判断

原稿的 Ledger 状态、回执重放、三个编号、数据库唯一约束与事务都必须保留。这次沿用订单排查助手，增加“在允许的工作区保存诊断报告”的教学任务，并调整几处解释顺序。

- 原稿先用退款、再用 answer.txt 切换场景；候选直接从诊断结果写入文件后回执丢失开始。付款与发信只用作副作用边界提醒，不执行真实业务操作。
- 标题已有“幂等”，正文却较快进入幂等键。候选先给出幂等性的定义，再区分调用、尝试与业务动作，避免把相同参数 Hash 当成同一动作。
- 原稿先讲重放，最后才讲对账。候选把两者放在同一节：已有结果时重放，结果不明时核对外部证据，不能确认时保持 unknown。
- 保留两段 SQLite 小实验，先说明为什么 JSONL 的“查完再写”不能裁决并发，再分别演示唯一约束和同一事务。恢复资格、外部副作用与数据库事务的边界不能混同。

## 结构对比

| 原稿内容 | 候选组织 | 读者要带走的判断 |
| --- | --- | --- |
| running、终态与 result 的记录顺序 | Ledger：记录执行状态与结果 | 必须先记录可能开始执行，再保存终态与可回放结果 |
| 三个编号与 Hash | Idempotency：业务效果与请求身份 | 相同动作的安全重试沿用幂等键，新执行尝试用自己的编号 |
| 补回执与章末 unknown 对账 | Recovery：回执重放与外部对账 | 对话缺消息不等于工具没执行，当前目标满足也不证明历史执行次数 |
| 两个 Worker 先查后写 | 并发去重：唯一约束与执行资格 | 执行资格须由原子约束裁决，不由两次独立查询裁决 |
| 两张表同步更新 | 事务一致性：事件历史与当前状态 | 事件与当前状态一起提交；事务不涵盖外部文件和支付动作 |

保留原章标题和三个核心代码片段，不把本章变成数据库教程。报告内容在小实验中简化为 done，用于观察写入与回执，不代表完整业务报告。
