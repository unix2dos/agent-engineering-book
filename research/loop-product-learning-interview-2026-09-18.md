# Loop 产品目标与开发过程学习：访谈记录

日期：2026-09-18。状态：产品方向、学习方式、首个 Coding 任务与日期信息来源已确认；运行授权与旧会话提示词更新策略也已确认，进入分步实现。

## 1. 用户已经明确的方向

- Loop 应让第一次接触 Agent 的新手直观看见真实执行轨迹。
- 当前系统提示词过于限定资料阅读，连询问当天日期也无法自然处理，影响基本使用体验。
- 作者希望在优化 Loop 的过程中得到知识解释和新概念提醒，学习与真实工程问题相连。
- 有价值的知识可沉淀到 agent-engineering-book。
- 本轮先做双向钢人论证和 grill-with-docs 访谈，再决定如何实现。

需要区分三个对象：Loop 执行用户任务；Loop 向新手呈现可核对的执行过程；开发协作向作者解释工程取舍。第一轮已确认：首版以清楚的轨迹为主，不同时加入产品内 AI 讲解入口；作者的知识讲解由开发协作承担。

“先 list_files”是提示词要求，不是程序强制调用顺序。上述两轮没有工具调用，也说明不能把模型指令等同于代码强制执行。

## 3. 双向钢人论证

支持调整方向的最强理由：自然的小任务可以同时提供使用价值和可观察机制。用户不必先接受文件阅读课的任务设定；日期、资料与后续操作按实际需要选择信息来源。作者从真实改动中学习上下文、工具与权限的区别，并把可复核的案例写入书稿。

反对直接放宽为通用 Agent 的最强理由：提示词放开不等于能力就存在，日期缺少来源时可能只是从诚实拒答变成猜测。为了通用不断增加联网、写入和命令能力，会提高开发与教学复杂度；无关的工具调用、密集日志及未经验证的开发心得，也可能损害新手理解。

真正的分歧是首版承诺多大能力、哪些观察对新手最有价值、知识讲解在开发中的打断程度，以及工程经验达到什么证据标准后进入书籍正文。

只读环境核查：本机 Docker CLI 与服务端均可连接，当前 context 为 OrbStack，服务端为 linux/arm64。尚无缓存的官方 Golang 镜像。本次只运行命令位置、版本和 daemon 信息检查，没有拉取镜像、创建容器或验证隔离策略。

## 5. 可从本次问题提炼的知识

- 提示词、运行时上下文、工具能力与执行权限是不同责任：改提示词不能替代提供事实来源或实现工具。
- 轨迹应记录实际来源。如果时间由程序注入，要记录为上下文；不能画成从未执行过的工具调用。
- “没有检查”“检查后没发现”“不能取得信息”是不同的证据状态。回答中的断言应与已观察到的行为对应。
- 持久化会话带来提示词版本问题：既要保留当时的历史证据，也要明确新的会话策略从何时生效。
