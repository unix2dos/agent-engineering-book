# 实践札记：为什么 Agent 不知道今天几号

日期：2026-09-18。项目：Loop。对应实现：context.go 的 BuildTurnMessages，以及 trace.go 的 RunTask。核心实现已包含在 Loop 提交 e4daff34faf6c7fe074fb7ae8e2dad4cfeadc7fc 中。

## 1. 现象与原因

用户在已有对话中询问“今天多少号”，模型回答没有时钟工具，并把话题引回 Markdown 阅读。检查真实请求后发现，程序只发送了旧的资料助手提示词、历史对话和两个文件工具定义，没有发送当前日期或时区。

Run 的 created_at 只存在于运行记录中。程序知道什么时候启动了任务，不等于模型的输入里已经有这条信息。只把“资料助手”改成“通用助手”，不能补上缺失的事实来源。

## 2. 核心规则和动态上下文分别负责什么

核心规则说明如何行动：普通问题可以直接回答，需要现场信息时按需使用工具；声称已经读取、修改或执行，必须有实际结果支持。

动态上下文提供本轮环境事实：程序读取的日期、时间、时区、工作区和当前文件访问范围。时间来自 server_clock，记录 observed_at、date 和 time_zone。它是本轮开始时的服务端快照，不是持续更新的时钟，也不自动代表用户所在时区。

这次采用上下文提供时间，没有增加时钟工具。轨迹将这一步显示为 CONTEXT；工具调用数为零是正常结果，不应为了让流程更长而补画一次工具调用。

## 3. 历史记录与当前输入不是同一个对象

旧 Run、session.jsonl 和源码快照保留当时的事实。下一轮从其中取得消息，再建立新的模型输入：

```text
当前核心规则 + 本轮环境快照  → 一条新的 system 消息
历史 user / assistant / tool → 保留原内容及工具调用配对
本次用户消息                → 追加到末尾
```

旧 system 不再原样复制到新请求里，避免旧的角色限制和昨天的日期继续主导对话。每轮仍只有一条当前 system 消息；不会每追问一次就再叠加一份日期。

这是一次输入视图的重建，不是改写历史。实现先创建新消息切片，再追加历史中的非 system 消息；没有写回父运行的日志文件。

## 4. 怎样证明改动有效

自动检查覆盖同一时刻在 UTC 与 UTC+8 下的不同日期、跨日刷新、单条 system、历史工具消息配对不变、父消息对象不变，以及轨迹里的 system 与实际模型输入一致。Go race 检查和 19 项前端检查通过。

真实 GLM 验证沿用了旧对话的副本：父运行 a175592a831740838549926d7ac8414d 原先无法回答日期；新运行 db91c0086bfa452e85605e4247454db4 追问“今天多少号？按哪个时区算的？”。

- 本轮快照：2026-09-18T12:43:12+08:00，CST（UTC+08:00）。
- 实际模型请求 1 次，工具调用 0 次，正常结束。
- 回答给出 2026 年 9 月 18 日和 UTC+08:00，并明确依据服务端快照。
- 网页保留旧回答和新回答，显示完整三个 Turn；新的 CONTEXT 行能看到日期与时区。

证据位于本机 `~/.loop/checks/context-policy-20260918/`。验证记录保存的 BuildTurnMessages 函数源码与当前实现一致。这是一个日期问答与历史升级的实际样例，不能据此断言模型在所有问题上都可靠。

## 5. 验证中遇到的数据目录迁移

验证期间，另一个终端将项目内的 .agent_state 迁移到 ~/.loop。旧的验证服务已经启动，仍持有原来的绝对路径；因此列表中有已载入的摘要，但按旧路径读取详情返回失败。

迁移后比对了迁移前保存的哈希：19 份正式运行对应的 57 个原始文件全部一致，没有缺失或改写。将服务指向新目录后，正式历史和三轮验证对话均恢复显示。

这里的问题是进程中的路径状态没有随目录移动更新。不能把详情读取失败直接判成记录被删除，也不能只凭列表摘要还在就认定磁盘文件仍位于旧路径。数据迁移还要衔接使用这些数据的进程。

## 6. 当前边界

本步完成了通用对话提示、每轮时间上下文和旧对话的新规则使用。文件工具仍然只读 Markdown；Coding 练习的文件修改和容器测试尚未接入。

下一步按已确认方案提供独立 Go 练习：授权本次练习后自动读、改、测，只挂载练习项目，测试时禁用网络。当前仓库同时出现了公共部署模式，新增写入及命令能力不能因此自动扩大到匿名公网访问；具体接入时需保留已授权的本机练习边界。
