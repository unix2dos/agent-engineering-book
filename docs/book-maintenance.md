# 教材维护约定

作者工作资料，不进入书籍目录。读者入口是[正文目录](../SUMMARY.md)和[配套实践](../practice/README.md)。

## 内容与实践

一章围绕一个主要读者问题，正文解释问题、设计、关键代码与结果；每章只指向一个实践说明。实践写清必做操作、完成标准和选做范围。第 0～2 课不硬配代码，后续能力逐步积累到一个 Workspace Agent。

最小演示可以直接运行，综合实现已提供。阶段实践选择少数核心判断手写，以解释流程、修改小需求和验证正常／失败边界为主要交付。通用 Python、SDK 和测试脚手架不重复设关卡。

订单排查作为贯穿案例，减少反复熟悉背景的成本；其他案例只在更能说明机制时使用。独立安全、Tracing、交接和恢复实验明确说明尚未集成的部分，不把教学检查写成生产保证。

完成并合入的候选稿和修改对比由 Git 保存，不维护第二套全文。正式演示和检查放在本课实践，研究依据保留在 research；不建立通用教学框架或空的后续课次。

## 研究材料的归属

`research` 只维护来源、固定版本和结论边界，不重复维护当前学习进度、运行步骤或已定稿全文。解释机制的内容在正文维护；代码、执行条件与实测记录放在对应实践；当前路线与写作约定在 docs 维护。已完成的提纲、旧句修改对比和待办交由 Git 历史保存。

已有来源记录是带日期的核验快照。整理目录或离线检查通过，不代表重新确认了外部项目的最新行为；保留版本、日期、原始指纹和未验证范围。

## 写法

标题与关键术语保持专业，保留有层次的小标题、必要的对照表和流程图。案例引入问题，节内用通俗语言解释机制，术语首次出现时解释清楚；之后使用同一名称，不用比喻替换正式概念。

`ljg-writes` 用于组织章节与小节的递进，`ljg-plain` 用于解释难懂的段落；本书保留 Markdown 章节结构，不采用“全文无子标题”的格式。每课应有能在书内看懂的过程或结果，配置与完整脚手架放配套实践。不靠字数、笑话或插图配额制造一致性。

已有章节的实质改写先提供对比，确认后应用。已确认的目录、实践入口与引用整理可直接落实。提交和发布另行确认；遇到范围改变或证据不足先讨论，不补造运行结果。
