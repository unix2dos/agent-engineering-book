# 第 3 课：Tool Calling Loop——从调用请求到最终回答

你让 Agent 计算 `248 × 15`。模型可以给出一个听起来很确定的答案，但语气坚定不是乘法验算。

给它接上乘法工具以后，过程变成：

```text
模型申请 multiply(248, 15)
→ Python 算出 3720
→ 程序把结果交回模型
→ 模型回答：结果是 3720
```

模型负责提出申请，程序负责执行和回传。这条反复进行的流程，就是 **Tool Calling Loop**。先用没有文件和网络副作用的乘法，看清它怎样闭合。

## 1. 一次计算，为什么有四条消息？

这个任务留下四条 Message：

```text
User：计算 248 × 15
Assistant Tool Call：申请 multiply，编号 call_1
Tool Result：call_1 的结果是 3720
Assistant Final：结果是 3720
```

它们来自两次模型请求。第一次把用户问题和工具说明交给模型，拿到调用申请；程序执行工具后，第二次把前三条消息一起发回，才得到最终回答。

因此，这里是四条消息、两次模型请求、一次工具执行，完成一个用户问题。从用户提问到最终回答的整段交互，叫一个 **Turn**。

模型写出工具名称，并不会让 Python 自动执行。第 2 课里的 Harness 要接住申请，检查参数，调用函数，再把结果放回消息列表。

## 2. 给模型一个受限工具

先定义乘法。下面的函数只接受范围内的整数：

```python
def multiply(a, b):
    if type(a) is not int or type(b) is not int:
        raise ValueError("a 和 b 必须是整数")
    if abs(a) > 1_000_000 or abs(b) > 1_000_000:
        raise ValueError("数字太大")
    return a * b

print(multiply(248, 15))
```

输出是 `3720`。这里使用精确类型判断，也会拒绝 Python 的布尔值；不能让 `True` 偷偷充当整数 1。

不要把模型生成的字符串交给 `eval()` 计算。它执行的是 Python 代码，不是受限的数学表达式。工具应接受数据，执行预先定义好的动作。[1]

模型还需要一份工具说明，叫 **Tool Schema**。其中的核心内容可以写成：

```json
{
  "name": "multiply",
  "description": "计算两个整数的乘积",
  "parameters": {
    "type": "object",
    "properties": {
      "a": {"type": "integer"},
      "b": {"type": "integer"}
    },
    "required": ["a", "b"],
    "additionalProperties": false
  }
}
```

它说明工具名、必填参数和允许的类型。不同 API 的外层包装可能不同；本章使用常见的 Tool Call / Tool Result 消息关系，接入时按 Provider 协议适配。[2]

Schema 帮助模型填对申请，执行侧仍要检查真正收到的数据。它既不会替你执行函数，也不是权限证明。

## 3. 接住申请，生成对应的回执

模型申请乘法时，工具调用可以表示为一个字典。下面沿用刚才的 `multiply()`，把检查和调用放进 `execute_tool()`：

```python
import json

call = {
    "id": "call_1",
    "type": "function",
    "function": {
        "name": "multiply",
        "arguments": '{"a":248,"b":15}',
    },
}

def execute_tool(call):
    try:
        function = call["function"]
        if function["name"] != "multiply":
            raise ValueError("未知工具")
        arguments = json.loads(function["arguments"])
        if not isinstance(arguments, dict) or set(arguments) != {"a", "b"}:
            raise ValueError("multiply 只接受 a 和 b")
        value = multiply(arguments["a"], arguments["b"])
        payload = {"status": "completed", "result": value}
    except (ValueError, KeyError, TypeError) as error:
        payload = {"status": "error", "message": str(error)}
    return json.dumps(payload, ensure_ascii=False)

print(execute_tool(call))
```

输出为：

```json
{"status": "completed", "result": 3720}
```

`arguments` 是 JSON 字符串，`json.loads()` 把它变成字典；执行后，`json.dumps()` 再把结果转成可回传的文字。负责按工具名找到实现并检查申请的这段逻辑，通常叫 **Router（工具路由器）**。

工具结果还要带上原调用编号。若模型同一批提出两个调用：

```text
call_1：248 × 15 → 结果必须带 tool_call_id=call_1
call_2：  6 ×  7 → 结果必须带 tool_call_id=call_2
```

编号是回执找到申请的依据。先保存完整 Assistant Tool Call，再追加各条 Tool Result；失败或拒绝也要带回自己的编号，不能把那条结果悄悄丢掉。

## 4. 把消息接成一个循环

循环每次请求模型后，只做三种选择：执行工具后继续，返回最终回答，或停止并报错。

下面用 `ask_model(messages)` 表示模型接口。它接收消息，返回取出外层包装后的字典，其中包含 `finish_reason` 和 `message`。真实接入时，由这个接口负责发送工具说明并适配 SDK；循环本身不依赖某个 SDK 对象。

沿用上一节的 `execute_tool()`：

```python
def run_loop(ask_model, question, max_requests=4):
    messages = [{"role": "user", "content": question}]
    for step in range(max_requests):
        print("模型请求", step + 1)
        response = ask_model(messages)
        message = response["message"]
        reason = response["finish_reason"]
        calls = message.get("tool_calls") or []

        if calls and reason != "tool_calls":
            raise RuntimeError("Tool Call 与停止原因不一致")
        messages.append(message)

        if calls:
            for call in calls:
                result = execute_tool(call)
                print("工具结果", result)
                messages.append({
                    "role": "tool",
                    "tool_call_id": call["id"],
                    "content": result,
                })
            continue

        if reason == "stop":
            return message.get("content") or ""
        raise RuntimeError("模型没有正常结束")

    raise RuntimeError("超过模型请求次数上限")
```

`continue` 表示回到循环开头。只有本批工具结果全部写进消息后，才再次请求模型。没有工具调用并且 `finish_reason="stop"`，才能走正常返回分支；其他结束状态不能冒充 Final。

为了在书内看见完整过程，用一个按固定规则应答的函数扮演模型：第一次返回上面的乘法申请，第二次读取工具结果并回答。

```python
def scripted_model(messages):
    if len(messages) == 1:
        return {
            "finish_reason": "tool_calls",
            "message": {"role": "assistant", "tool_calls": [call]},
        }

    result = json.loads(messages[-1]["content"])
    return {
        "finish_reason": "stop",
        "message": {
            "role": "assistant",
            "content": "结果是 " + str(result["result"]),
        },
    }

print(run_loop(scripted_model, "计算 248 × 15"))
```

将本章 Python 代码按顺序放在一起，会先显示前两段的结果。最后一行再输出：

```text
模型请求 1
工具结果 {"status": "completed", "result": 3720}
模型请求 2
结果是 3720
```

这个模拟器只演示本例的成功路径。它证明循环怎样组织消息，不能证明真实模型一定会选择乘法工具。接上真实模型后，还要验证工具能力、返回协议和实际行为。

## 5. 参数写错了，为什么有时继续、有时必须停？

假设申请完整，但多了一个工具不接受的字段：

```json
{"a":2,"b":3,"command":"whoami"}
```

路由器会拒绝它，返回：

```json
{"status":"error","message":"multiply 只接受 a 和 b"}
```

程序将这份错误作为带原编号的 Tool Result 交回模型，模型下一轮可以修正参数。数字类型或范围不对，也按这种方式反馈；不会执行多出来的命令。

另一种情况是 Provider 表明响应因长度限制被截断，即 `finish_reason="length"`，消息中却还带着 Tool Call。它可能只生成了半份参数，也可能看起来完整；这批请求都不能直接执行。

```text
完整请求，参数不合要求 → 返回错误回执，让模型有机会修正
响应截断或状态矛盾   → 不执行工具，停止当前循环
```

上一节的循环在执行前检查了这条边界。以后可以设计重新请求的恢复策略，但不能先执行可疑申请，再靠结果判断是否安全。

如果模型反复犯错，最大请求次数会让循环停下来。次数上限限制的是模型请求数，不是消息数或工具数；每次网络请求还需要超时，SDK 的额外重试和费用也要纳入预算。踩住刹车可以停住车，不能顺便修好发动机。

到这里，我们已经有一条可以观察的工具闭环：模型申请，程序验证并执行，结果按编号回传，模型继续或结束。消息目前仍在内存里；程序退出后怎样继续，下一课再用 Session、Transcript 与 Checkpoint 解决。
