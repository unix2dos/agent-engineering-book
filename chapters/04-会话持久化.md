# 第 4 课：Session 持久化——Transcript、Checkpoint 与 Memory

假设你告诉 Agent：“部署前先运行测试。”它答应记住。重启终端后，你问下一步做什么，它却请你重新介绍项目。

承诺是永久的，保存位置却是内存。如果应用只把对话留在进程变量里，退出后就无法自动把它们交给下一次模型请求。

把数据写进磁盘可以保住记录，但还要分清：哪些交互属于同一段会话，哪些是当前进度，哪些规则以后仍然有效。

## 1. Session 先回答“这些记录属于谁”

从“检查配置”到“运行测试”，多次交互可以属于同一段会话，用共同的 `session_id` 关联。这段连续会话就是 **Session**。

例如 `session_id="demo"` 可以对应一个聊天页面，也可以对应一次可以退出后继续的命令行会话。编号帮助应用找回记录，本身不会替模型保存或读取内容。

Session 是逻辑上的归属，不规定必须使用某种文件。可以把它存成文件、数据库记录，也可以让模型服务管理对话并返回 Conversation ID。[1] 保存在哪里改变了实现方式，不改变它回答的问题。

## 2. Transcript 是流水，Checkpoint 是某个位置的状态

要追查会话过程，就按顺序保存消息和相关事件。这份有序记录叫 **Transcript**。要让程序从某个已知状态继续，可以再保存一份快照，叫 **Checkpoint**。

把 Session 暂时想成一个账户，先用三笔流水看清两者的关系：

```text
第 1 笔：存入 10 元
第 2 笔：支出 3 元
第 3 笔：存入 5 元
```

完整流水可以算出余额 12 元。如果第二笔之后已有“余额 7 元，已处理两笔”的快照，就只需再处理第三笔：

```python
events = [10, -3, 5]

balance = 0
for amount in events:
    balance += amount
print(balance)

checkpoint = {"processed": 2, "balance": 7}
balance = checkpoint["balance"]
for amount in events[checkpoint["processed"]:]:
    balance += amount
print(balance)
```

输出都是 `12`。`processed=2` 表示前两笔已经计入，恢复时从第三笔开始；快照中的状态必须与这个位置对应，才能避免重复或遗漏。

这个例子展示了区别：流水能解释“怎样到这里”，快照能帮助“从这里继续”。只有余额 12 元，无法还原前面是哪三笔；只有完整流水，则可能每次都要从头计算。

放回 Agent，就是：

```text
Session demo
|-- Transcript：用户、模型与工具按顺序说过和做过什么
|-- Checkpoint：截至某个位置，程序已经保存了什么状态
```

Agent 的状态可以包含历史摘要、已完成轮次、当前步骤和恢复位置，取决于应用准备支持什么恢复。Checkpoint 不要求复制整个进程，也不自动包含所有历史。

## 3. JSON 与 JSONL，怎样承载这些记录？

一份 JSON 可以保存最新状态，每次更新后整体替换。下面把会话编号和当前进度写入文件，再读回来：

```python
import json
import tempfile
from pathlib import Path

with tempfile.TemporaryDirectory() as folder:
    state_file = Path(folder) / "session-demo.json"
    state = {
        "session_id": "demo",
        "summary": "已检查配置，尚未运行测试",
    }

    temporary = state_file.with_suffix(".tmp")
    temporary.write_text(
        json.dumps(state, ensure_ascii=False), encoding="utf-8"
    )
    temporary.replace(state_file)

    restored = json.loads(state_file.read_text(encoding="utf-8"))
    print(restored["session_id"])
    print(restored["summary"])
```

输出为：

```text
demo
已检查配置，尚未运行测试
```

先写完整临时文件，再在同一文件系统中替换目标，可以避免读到覆盖过程中的半份 JSON。这个例子演示单进程存取；断电持久性、并发写入还需要额外保证。演示结束会清理临时目录，真实应用使用需要长期保留的位置。

Transcript 则适合追加：旧记录不动，新事件写到末尾。JSONL 就是一行一个完整 JSON 对象：

```jsonl
{"type":"message","role":"user","content":"检查配置"}
{"type":"message","role":"assistant","content":"配置有效"}
```

它不能作为一个 JSON 对象一次读入，需要逐行解析。所有事件也可以放进 JSON 数组，只是朴素实现增加事件时通常要重写整个数组。

Checkpoint 可以单独保存，也可以作为一条事件插入同一份 JSONL：

```text
第 1 行：消息
第 2 行：消息
第 3 行：Checkpoint，记录第 2 行之后的状态
第 4 行：新消息
```

恢复时先取最近的快照，再处理它后面的事件。一份文件既保存历史又包含恢复点，并不矛盾。**Transcript 和 Checkpoint 描述用途，JSON 和 JSONL 描述组织方式**。

上面的 JSONL 只展示事件形状，不是完整模型 API 请求；真实消息还要保留对应的角色和工具调用字段。

## 4. 换一个 Session，什么还应该记得？

“已经检查配置，下一步运行测试”属于当前任务进度。换一个新会话，不应无缘无故继承这项进度。

“部署前必须运行测试”是项目规则，“默认用中文回答”是用户偏好。它们可能跨会话仍然适用，因此需要单独保存为 **Memory（长期记忆）**。

| 内容 | 通常属于哪里 |
| --- | --- |
| 当前任务做到哪一步 | 当前 Session 的状态或摘要 |
| 同一项目多次会话都要遵守的约定 | 项目 Memory |
| 换项目后仍适用的个人偏好 | 用户 Memory |
| 当时具体发生过什么 | Transcript |

保存以后，应用还要主动选择哪些材料进入当前请求。下面只打印选出的材料，比较继续旧会话和开启新会话：

```python
checkpoint = {
    "session_id": "demo",
    "summary": "已检查配置，尚未运行测试",
}

def context_materials(session_id):
    materials = ["默认使用中文", "部署前先运行测试"]
    if session_id == checkpoint["session_id"]:
        materials.append(checkpoint["summary"])
    return materials

print("旧会话：", context_materials("demo"))
print("新会话：", context_materials("new"))
```

输出为：

```text
旧会话： ['默认使用中文', '部署前先运行测试', '已检查配置，尚未运行测试']
新会话： ['默认使用中文', '部署前先运行测试']
```

新会话没有旧进度，但同一用户、同一项目的长期材料仍可以使用。这个函数没有调用模型；只有把材料按消息规则加入实际请求，模型才有机会使用它们。

磁盘上保住了数据，叫持久化；本次实际交给模型的内容，才是 Context。存下一百条记录，并不意味着每次请求都应该带上一百条。

Memory 也不能照抄全部 Transcript。临时日志、未经确认的猜测和凭据，不应自动变成长久事实。只保留来源可信、允许保存且以后有用的内容，并支持更新和遗忘。

偏好冲突由应用按明确规则处理。例如用户这次要求英文，可以覆盖默认中文偏好；强制安全策略则不能被一句新偏好推翻。摘要或记忆中的文字，也不能被自动提升为新指令。

## 5. 旧 Checkpoint 不能证明工具没有执行

一种简单实现是在完整 Turn 结束后保存状态。一个 Turn 从用户提问开始，到模型最终回答结束，中间可以包含工具调用。未完成的一轮不能冒充已完成进度。

但如果文件已经写好，程序却在保存 Tool Result 前崩溃，磁盘上的 Checkpoint 可能仍停在上一轮：

```text
Checkpoint：还没开始本轮任务
真实文件：本轮修改已经发生
```

旧快照只说明应用最后成功保存到了哪里，不能证明外部动作没有发生，更不能证明执行了几次。

要恢复这种中断，需要另外记录工具何时获准、何时开始，以及是否有可核对的结果。第 6 课会把这份执行账本叫作 Ledger，并讨论怎样避免重复执行。

Checkpoint 也可以设计为保存中途状态，但必须包含恢复所需的现场。“只在最终回答后保存”是一种教学选择，不是 Checkpoint 的定义。

## 6. JSONL 写到十万行，就该换数据库吗？

假设启动时要找出所有最新状态为 unknown 的执行。unknown 表示工具是否完成仍无法确认。

文件里有四条记录：

```jsonl
{"execution_id":"exec_1","status":"running"}
{"execution_id":"exec_1","status":"unknown"}
{"execution_id":"exec_2","status":"unknown"}
{"execution_id":"exec_2","status":"succeeded"}
```

只搜索 unknown，会错把 exec_2 也找出来。程序要按执行编号整理最后状态，才能只留下 exec_1。

偶尔从头读一遍，JSONL 足够直接；每次启动都查、多处同时更新，程序就会逐渐需要索引、事务和并发控制。该不该换存储，要看这些读写要求：

| 主要需求 | 可以从哪里开始 |
| --- | --- |
| 整体保存一份最新状态 | JSON |
| 单进程顺序追加，偶尔回放 | JSONL |
| 本机频繁查询，需要事务和唯一约束 | SQLite |
| 多台机器共同读写 | 服务端数据库 |

十万行偶尔读取一次，未必需要迁移；一万行却被频繁全量整理，数据库可能已经更省事。JSONL 与 SQLite 没有高低级之分，变化的是程序需要哪些保证。[2]

换成数据库后，Session 仍归集会话，Transcript 仍保留历史，Checkpoint 仍提供恢复状态，Memory 仍保存长期事实。下一课继续解决：历史越来越长时，怎样在有限窗口内选择模型本次需要的内容。
