# 第 1 课：Agent 基础——从语言模型到行动系统

假设你对一个没有接入工具的语言模型说：“查一下明天上海的天气。如果下雨，在明早八点添加带伞提醒。”

它回复“已经安排好了”。日历里没有提醒，聊天框里倒有一份完整的竣工报告。

问题很具体：系统只生成了文字，没有查询天气，也没有创建提醒。要让一句话变成动作，还需要运行模型之外的程序。

## 1. 一句回答怎样变成真实动作？

模型可以写出 `read_file`、`send_email` 或 `create_reminder`，却不会因此获得文件、邮箱和日历的权限。

应用需要把可用能力告诉模型，接住它提出的调用，检查能否执行，再把实际结果交回去：

```text
用户提出要求
→ 模型申请查询天气
→ 程序调用天气工具，拿到结果
→ 模型根据天气提出后续动作
→ 程序检查并创建日历提醒
→ 模型根据真实结果回答
```

这是一个可能的运行过程，不表示所有天气提醒都需要模型来安排每一步。它先说明一个边界：**提出动作和真正执行，是不同的工作**。

是否创建成功，要看日历服务的结果，不能只看模型说了什么。模型也不能通过写一句“已批准”，替自己扩大执行权限。

## 2. 下一步由代码规定，还是由模型选择？

天气提醒可以写成固定流程：

```text
查询天气
→ 若下雨，创建提醒
→ 否则，不创建
→ 返回结果
```

这种由程序预先安排步骤和分支的系统，叫 **Workflow（工作流）**。它也可以调用模型，例如把天气说明整理成数据；也可以有条件判断和重试。出现不同分支，不代表它自动变成了 Agent。

另一种任务是：“查清这次构建为什么失败。”开始前很难列出每一个调查动作。模型可能先读错误日志，再查配置；如果证据不够，就检查依赖或询问用户。把这部分推进任务的决策交给模型，就是本书讨论的 **Agent**。[1]

| 方式 | 控制过程的特点 |
| --- | --- |
| Workflow | 步骤和分支规则由代码预先规定 |
| Agent | 模型在允许范围内，根据目标和新结果选择怎样推进 |

两者可以组合。调查失败原因由 Agent 决定，部署前的测试、审批和发布步骤仍由固定流程控制。模型选择行动路线，不等于它能修改这些边界。

要依据工具结果继续决定，就需要反复进行：

```text
模型选择动作 → 程序执行 → 结果返回 → 模型继续选择
```

这段循环叫 **Agent Loop**。ReAct 则是推理、行动和观察交替的一种具体组织方法。[2] 看到工具循环，不能直接断言系统使用了 ReAct；现代工具调用也不要求公开模型的完整思考过程。

## 3. 先选最小方案

Agent 的灵活性需要付出代价：更多模型请求、等待和失败路径。只有根据现场信息调整路线的收益足够大，这些成本才值得承担。

| 需求 | 可以从哪里开始 | 原因 |
| --- | --- | --- |
| 翻译一句话 | 一次模型调用 | 不需要外部行动和持续循环 |
| 查询数据、生成日报、确认后发送 | Workflow | 主要步骤和分支可以提前规定 |
| 调查未知故障，随证据调整排查方向 | Agent | 下一步依赖尚未取得的信息 |

固定日报即使使用模型和邮件工具，也可以是 Workflow。反过来，在 Prompt 里写“你是 Agent”，不会让文本生成自动获得执行能力。

拿到需求后，先列出确定的步骤，再标出真正需要判断的部分。例如“先检查格式，再运行测试，批准后发布”适合交给代码；“测试失败后该查日志、查依赖还是改配置”可以让模型根据证据选择。

不要因为任务复杂，就把所有步骤都交给 Agent。让确定流程负责稳定推进，让模型处理需要适应变化的部分。下一课再沿一次工具调用，认识支撑这套系统的 Model、Harness、Tool 与 Environment。
