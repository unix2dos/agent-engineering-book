# 第 5 课：从完整 Transcript 到有限 Prompt View

Agent 执行了一次测试命令，终端吐出 200KB 日志。若把整份日志塞进下一次请求，Model 的窗口可能装不下；若直接删掉，真正的错误又可能恰好藏在中间。

更实用的办法是：完整日志留在磁盘，本次只把最有用的一小段交给 Model。会话越来越长以后，旧消息也采用相同思路。

怎样在不丢失原始记录的前提下，决定这一轮给 Model 看什么，就是本章要解决的问题。这个工作通常叫上下文工程。

## 1. 完整日志和本轮输入为什么要分开？

先把测试日志放回整个会话：

```text
用户要求运行测试
-> Agent 执行命令
-> 产生 200KB 完整日志
-> 本轮只返回最后一段错误和完整日志路径
-> Model 根据错误继续修改代码
```

这里出现了四种不同的东西。先看它们各自做什么，再记名字：

| 说人话 | 正式名称 | 例子 |
| --- | --- | --- |
| Tool 产生的完整文件 | Artifact | Bash 完整日志、构建产物 |
| 会话按顺序保存的记录 | Transcript | User、Tool Call、Tool Result、Final |
| 把旧历史改成摘要后留下的恢复点 | Compaction Entry | Summary、保留原文和切点信息 |
| 本轮真正递给 Model 的内容 | Prompt View | 摘要、最近原文和当前 Turn |

完整 Bash 日志是 Artifact。谁要求运行命令、Model 怎样申请工具、Tool Result 返回了什么，则属于 Transcript。它们都可以留在磁盘，Harness 每轮只挑当前有用的部分组成 Prompt View。

```text
Artifact / Transcript / Memory
              |
              | Harness 按预算选择
              v
          Prompt View
              |
              v
            Model
```

会话太长时，Harness 会把较早内容写成摘要，并保留最近原文。这个动作叫 Compaction。动作成功后，会在会话存储（Session Store）中写下一条恢复记录，这才是 Compaction Entry。

第 4 课只保存一份最新 Checkpoint，所以使用 JSON，每次整体替换。现在要保存 Transcript，旧事件不能被新事件覆盖，写法变成：每发生一件事，就在文件末尾追加一行。

这种“一行一个 JSON 对象”的文件叫 JSONL，也就是 JSON Lines：

```jsonl
{"type":"message","message":{"role":"user","content":"运行测试"}}
{"type":"message","message":{"role":"assistant","content":"测试失败"}}
```

每一行单独看都是完整 JSON。整份文件却不是一个 JSON 对象或数组，所以程序不能用一次 `json.load()` 读取它；需要逐行调用 `json.loads(line)`。

```text
JSON：  一份完整状态，修改后整体替换
JSONL：多条独立事件，新事件逐行追加
```

JSONL 不是更高级的 JSON。它只是更适合 Transcript 这种按时间增长的流水。最小 Compaction Entry 也是其中一行：

```json
{
  "type": "compaction",
  "summary": "m1-m3 的摘要",
  "retained_tail": ["m4 原文", "m5 原文"],
  "is_split_turn": false
}
```

Model 不直接接收这层 JSON 外壳。Harness 把它展开成：

```text
summary + retained_tail + Compaction 后的新 Message
```

`summary` 是较早历史的摘要，`retained_tail` 是继续保留原文的最近消息。

被摘要的旧 Message 仍留在更早的 Transcript 中。

## 2. Pi 怎样处理 200KB Tool Result？

Pi 不会默认把所有工具输出都塞给 Model。`read_file` 常保留文件开头，也就是 Head；Bash 常保留输出末尾，也就是 Tail。完整日志另存成 Artifact。

文件开头往往包含声明和配置，命令末尾往往包含退出状态和最后一个错误。这只是一个常用猜法，不保证根因一定在那里。

如果错误在中间，Model 可以根据 Artifact 路径搜索完整日志，再读取命中附近的小片段。数据没有消失，只是没有一次性进入 Context。

```text
read_file -> 限制长度，返回 truncated 和 next_offset
run_bash  -> 返回受限 Tail、退出状态和 Artifact Path
write_file -> 返回路径、状态和写入 Byte 数
```

先限制一份过大的 Tool Result，通常比摘要整段对话更便宜，丢失的信息也更少。

工具结果变小以后，会话本身仍可能越来越长。Pi 会在 Context 快要挤满、但还没占完时执行 Compaction，提前为下一次回答留出空间。压缩后使用 Summary 加最近原文，旧记录仍留在存储中。[Pi Compaction](https://github.com/earendil-works/pi/blob/e266507b606b9552fa277252644054afd4384b11/packages/coding-agent/docs/compaction.md)

Pi Coding Agent 默认把 Session 追加到 JSONL。每条记录还带有 `id` 和 `parentId`，所以用户回到旧位置重新尝试时，可以追加一个新分支，而不用覆盖原来的尝试。[Pi Session Format](https://github.com/earendil-works/pi/blob/e266507b606b9552fa277252644054afd4384b11/packages/coding-agent/docs/session-format.md) Pi Core 也提供 SQLite Backend；这说明存储格式可以更换，完整历史与 Prompt View 的分工不变。

## 3. 历史从哪里切开才不会损坏 Tool Call？

一个很大的 Turn 可能是：

```text
User
Assistant(tool_call A)
Tool(result A)
Assistant(tool_call B)
Tool(result B)
Assistant(final)
```

下面两处不能切：

```text
tool_call A | result A
tool_call B | result B
```

它们会让一边只剩申请、另一边只剩回执。完整 Turn 之间是最容易处理的安全边界。

如果单个 Turn 本身已经超窗，Pi 允许 Split Turn：在已经闭合的 Tool Call/Result 之后切开，把前缀压成 Turn Prefix Summary，后面的消息保留原文。切点前的用户目标必须进入摘要，否则后半段不知道自己在完成什么。

当前综合实践采用更保守的第一版：`find_compaction_cut()` 只返回完整 Turn 结束位置；没有安全旧 Turn 时不压缩。它暂时不实现 Split Turn，这是一条有意保留的能力边界。

## 4. OpenClaw 为什么先处理旧 Tool Result？

会话跑了很多轮以后，最占地方的往往不是用户问题，而是以前读过的文件和命令输出。OpenClaw 可以只在下一次请求前，把这些旧 Tool Result 换成头尾片段或占位文字。磁盘里的完整 Transcript 不动。

这种“只缩短本次输入，不改磁盘历史”的处理叫 Pruning，也就是修剪。若连普通对话都已经太长，就把较早历史写成 Summary，并保存新的恢复点。这才是 Compaction。

| 机制 | 改变什么 | 是否写持久恢复点 |
| --- | --- | --- |
| Pruning | 请求前的旧 Tool Result 视图 | 否 |
| Compaction | 较早历史在后续 Prompt 中的表示 | 是 |
| Transcript | 保存完整会话事实 | 它本身就是持久记录 |

当前 OpenClaw 的 Compaction 会保护 Tool Call/Result 配对。若摘要没有通过质量检查，就不写入新的压缩点，原历史继续保留。[Session Pruning](https://github.com/openclaw/openclaw/blob/ad3268ecccbc7758878662b31adcd72475343d3e/docs/concepts/session-pruning.md)、[Compaction](https://github.com/openclaw/openclaw/blob/ad3268ecccbc7758878662b31adcd72475343d3e/docs/concepts/compaction.md)

Summary 仍可能漏掉跨 Session 有用的规则。因此 OpenClaw 默认会在 Compaction 前，先提醒 Agent 把稳定事实写入 Memory 文件。这个动作叫 Memory Flush，可以理解为“压缩前先把以后还要用的规则抄到长期笔记”。[OpenClaw Memory](https://github.com/openclaw/openclaw/blob/ad3268ecccbc7758878662b31adcd72475343d3e/docs/concepts/memory.md)

```text
稳定、跨 Session 有用 -> Memory
当前任务进度          -> Summary
完整发生事实          -> Transcript
```

Memory Flush 不是复制 Transcript。临时日志、失败尝试、未经确认的猜测和敏感内容通常不应晋升为长期 Memory。

OpenClaw 当前把普通 Session 和 Transcript 保存到每个 Agent 自己的 SQLite。旧 JSONL 主要用于迁移或归档；Incognito Session 才只留在内存中，Gateway 重启后就消失。[OpenClaw Session](https://github.com/openclaw/openclaw/blob/ad3268ecccbc7758878662b31adcd72475343d3e/docs/concepts/session.md) 存储从 JSONL 换成 SQLite，没有改变上面三种职责。

## 5. Hermes：Prompt 变短为什么可能更贵？

Model 会把文字切成较小的计量单位，这些单位叫 Token。假设每次请求开头都有相同的 30,000 个 Token，提供模型 API 的服务方（Provider）可以记住这段开头，下次直接复用已经算过的结果。这种“复用相同开头”的能力叫 Prompt Cache。

如果每轮都改写很早的一条消息，后面的整段开头也跟着变化，原来的缓存就用不上了。请求虽然少了 200 个 Token，却可能需要重新计算后面的几万个 Token。

Hermes 提供一种可选做法：每完成一轮，就把最老的一轮并入滚动 Summary。这样不会突然出现一次很长的摘要停顿，也能让窗口一直保持较低占用。这叫 Micro-compaction，也就是把一次大压缩分摊成很多次小压缩。[Micro-compaction](https://github.com/NousResearch/hermes-agent/blob/afc3d9d34c9c3b01fa2e1332d2c66a5b5fabae3f/docs/micro-compaction.md)

代价是旧内容更早变成摘要，而且每次改写早期历史都可能破坏 Prompt Cache。所以 Hermes 默认关闭它，让使用者根据真实成本决定是否开启。

```text
压缩净收益
= 回收的 Context 空间
- 摘要调用成本
- 缓存失效
- 延迟
- 语义损失
```

因此，Prompt 更短不自动等于请求更便宜。稳定前缀很大、缓存折扣很深时，频繁改写早期消息可能比偶尔批量 Compaction 更贵。

Hermes 当前使用 `~/.hermes/state.db` SQLite 保存 Session 和 Message，并提供全文搜索。[Hermes Session Storage](https://github.com/NousResearch/hermes-agent/blob/afc3d9d34c9c3b01fa2e1332d2c66a5b5fabae3f/website/docs/developer-guide/session-storage.md) 这同样只是保存方式，不改变“完整记录”和“本轮输入”的区别。

## 6. 三个项目最后都在做什么？

| 问题 | Pi | OpenClaw | Hermes |
| --- | --- | --- | --- |
| 持久 Session | CLI 默认 JSONL；Core 可选 SQLite | SQLite；Incognito 在内存 | SQLite |
| 大 Tool Result | 保留 Head/Tail，完整输出另存文件 | 请求前修剪旧结果 | 修剪旧 Tool Result |
| 持久压缩 | 写入 Compaction Entry | 在 Transcript 中保存 Summary | 一次批量压缩或逐轮更新 Summary |
| 长期事实 | 项目上下文文件 | 压缩前写入 Memory | 通过记忆扩展写入 |
| 特别权衡 | 分支树与 Split Turn | Transcript/Prompt/Memory 分层 | Prompt Cache 与摊销成本 |

共同点不是文件扩展名，而是：持久层保存可以追查的事实，Prompt View 只投影当前任务需要的内容。

## 7. 把这些做法放回我们的 Python Agent

配套实现分成两个入口：

- [`lesson_05_context_compaction.py`](../examples/lesson_05_context_compaction.py) 是完整参考实现，包含 Tool 输出限制、Artifact、Transcript、Compaction 和在线运行入口。
- [第一阶段综合实践](../exercises/phase-1-capstone/README.md)要求你亲手从 JSONL 追加、Prompt View、重启恢复一路写到请求前 Compaction。

综合实践第三关最终数据流是：

```text
User Message 先写入 Transcript
-> 请求前检查 Prompt 预算
-> 超预算时寻找完整 Turn 切点
-> summarize(prefix)
-> append Compaction(summary, retained_tail)
-> 从 Transcript 重新 build_prompt_view()
-> 把新 Prompt View 发给 Model
```

最容易漏掉的是倒数第二步。Compaction Entry 已经写盘，不代表内存里的旧 `messages` 自动改变。Harness 必须重新读取 Transcript，才能把新的 Prompt View 发给 Model。

Summary 像一根接力棒。第二次 Compaction 必须先拿到第一次的 Summary，再把新一段旧历史合进去：

```text
第一次：summary_1 = summarize(m1-m80)
        tail_1    = m81-m100

第二次：summary_2 = summarize(summary_1 + m81-m120)
        tail_2    = m121-m140
```

若第二次完全丢掉 `summary_1`，`m1-m80` 的信息就会离开未来 Prompt。只需要保留最新 `summary_2`，因为它已经接过前一棒；把所有旧摘要一起发送又会浪费空间。

最值得亲手写的是 JSONL 追加、Prompt View 组装、Compaction Entry 和完整 Turn 切点。摘要 Prompt、Token 估算适配和 Provider SDK 样板可以让 AI 帮忙。Pi 分支树、OpenClaw SQLite 与 Hermes Prompt Cache 只需读懂，不要复制整套框架。

本地 JSONL 示例帮助我们看清责任，但不能替代模型 API 服务方托管状态。OpenAI 和 Anthropic 都提供服务端 Compaction，应用自己的完整 Transcript、业务 Memory 和外部动作执行收据仍有独立价值。后面会把这份执行收据叫作 Ledger。[OpenAI Compaction](https://developers.openai.com/api/docs/guides/compaction)、[Anthropic Compaction](https://platform.claude.com/docs/en/build-with-claude/compaction)

下一课不急着把 JSONL 换掉，而是从一次具体查询开始判断：[什么时候该从 JSONL 换成 SQLite](06-什么时候从JSONL换成SQLite.md)？

## 主动回忆

1. Artifact、Transcript、Compaction Entry 与 Prompt View 分别保存什么？
2. Model 会直接收到 Compaction JSON 外壳吗？
3. Pruning 与 Compaction 分别改变什么？
4. 为什么从 JSONL 换成 SQLite，不会改变 Transcript 与 Prompt View 的分工？
5. Split Turn 的切点为什么不能落在 Tool Call 与 Result 之间？
6. 第 4 课使用 JSON，第 5 课为什么改用 JSONL？
7. Memory Flush 为什么不能复制整段 Transcript？
8. Prompt 变短为什么可能因 Prompt Cache 失效而更贵？
9. 第二次 Compaction 为什么必须继承旧 Summary？
10. Compaction 写盘后，为什么还要重新构造 Prompt View？

<details>
<summary>检查简答</summary>

1. Artifact 保存完整 Tool 产物；Transcript 保存会话事实；Compaction Entry 保存压缩恢复点；Prompt View 是本轮模型输入。
2. 不会。Harness 展开为 Summary、保留原文和后续 Message。
3. Pruning 只改请求视图；Compaction 写入持久 Summary，改变后续恢复视图。
4. JSONL 和 SQLite 都只是保存方式。Transcript 仍负责保存会话记录，Prompt View 仍是本轮送给 Model 的有限内容。
5. 否则一边只剩调用申请，另一边只剩无法配对的回执。
6. 第 4 课只保存一份最新 Checkpoint，适合整体替换 JSON；第 5 课要保留有序事件，适合逐行追加 JSONL。
7. Transcript 含临时、未经确认和敏感内容；Memory 只保存稳定且未来有用的事实。
8. 改写早期历史会破坏稳定缓存前缀，增加重算、延迟和缓存写入成本。
9. 新 Summary 必须覆盖旧 Summary 与新进入 Prefix 的消息，否则更早历史会丢失。
10. 磁盘增加 Entry 不会自动修改进程内已有的 `messages`。

</details>
