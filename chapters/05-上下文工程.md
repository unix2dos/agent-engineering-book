# 第 5 课：Context Engineering——Compaction 与 Prompt View

假设 Agent 运行了一次构建，工具返回 200KB 日志。你要它找报错，它却先读起了施工日记：欢迎语、下载进度、重复警告，一个也没少。

把完整日志塞进下一次请求，会占掉上下文预算；直接删掉，又可能丢失排错证据。更合适的做法是保留原始输出，本轮只递给模型需要的部分，缺什么再查。

上一课解决了会话怎样保存。这一课继续问：保存下来的东西，哪些应该进入下一次模型请求？围绕这个问题安排输入，就是 **Context Engineering（上下文工程）**。

## 1. 保存全部记录，本轮只看需要的部分

完整工具产物叫 **Artifact**，例如构建日志。Transcript 记录用户要求、模型申请、工具结果和回答。本轮真正递给模型的内容，则叫 **Prompt View**。

它们可以很不一样：

```text
磁盘：完整构建日志、完整会话记录
本轮输入：用户目标、必要历史、当前错误片段
```

先看一个裁剪例子。这里用四行文字演示取末尾两行，原始内容不变：

```python
full_output = "构建开始\n依赖检查完成\nERROR: config 缺少字段\n退出码 1"
lines = full_output.splitlines()
preview = "\n".join(lines[-2:])

print(preview)
print("完整输出仍有", len(lines), "行")
```

输出为：

```text
ERROR: config 缺少字段
退出码 1
完整输出仍有 4 行
```

`lines[-2:]` 表示取最后两行。真实工具还应保存完整输出，并返回可读取的位置；如果根因在中间，模型可以搜索完整日志，再读取附近片段。只返回尾部是一种选择，不保证错误总在结尾。

文件开头常有声明和配置，命令末尾常有退出状态，因此不同工具可以选不同片段。先缩短一份过大的工具结果，通常比立刻摘要整段会话更简单。

对已保存的旧 Tool Result，也可以只缩短本次请求中的表示。这类处理常叫 **Pruning（修剪）**：磁盘历史不动，本轮不再重复发送大段旧输出。[1]

## 2. 什么时候该压缩历史？

工具结果缩短以后，长期对话仍会增长。要给下一次输入和输出留出空间，不能等窗口完全塞满才处理。

模型窗口通常按 Token 计量。字节数、字符数和 Token 数不是同一个单位；200KB 日志占多少 Token，取决于内容与分词方式，不能只凭文件大小断言一定超窗。

假设窗口上限是 32,000 Token。下面全部是给定的演示数字：

```python
window = 32000
fixed_input = 4000
history = 23000
new_tool_result = 3000
output_reserve = 4000
safety_margin = 1000

required = (
    fixed_input + history + new_tool_result
    + output_reserve + safety_margin
)
print(required)
print(required > window)
```

输出为：

```text
35000
True
```

固定输入包括系统说明、工具定义等；输出预留是准备留给模型回答的空间。按这份计划，还需回收至少 3,000 Token，或者调整本轮输入与预算。

实际系统应按对应模型的计数规则或可靠估算测量全部请求内容，并计入协议开销。教学代码可以用字符数或字节数练习触发逻辑，但不能把这个近似当成真实 Token 预算。

如果旧历史已经占了大头，可以把较早内容概括成摘要，保留最近原文。这叫 **Compaction（压缩）**。它改变以后请求中历史的表示，并保存新的恢复点。被概括的原始消息仍然保留，方便追查。

核验版本的 Pi 会在窗口耗尽前预留空间，压缩较早历史并保留近期消息；再次压缩时继承旧摘要。[2] 关键是这条预算与恢复关系，不必照搬它的全部存储实现。

## 3. 从哪里切开，才不会把对话切坏？

一轮工具交互可能是：

```text
User：检查配置
Assistant：申请 read_file，编号 call_1
Tool：返回 call_1 的文件内容
Assistant：给出本轮回答
```

不能在申请和结果之间切开。否则模型只看到一张没有回执的申请，或者一条找不到申请的结果。同一条 Assistant 消息如果申请多个工具，相应结果也要按协议完整保留。

最容易处理的边界，是完整 Turn 之间：

```text
T1：User → Assistant Final                         可摘要
T2：User → Tool Call → Tool Result → Assistant Final 保留原文
T3：User → Tool Call                               尚未完成，保留
```

保留最近一轮完整对话时，可以在 T1 后切开，摘要 T1，原样保留 T2 和当前的 T3。没有安全的旧轮次，就不能为了达到长度目标硬切。

如果单个 Turn 已经很大，更复杂的实现可以在闭合的工具交互后切分，称为 Split Turn。它还需要在摘要中保留用户目标，保证后半段知道自己在做什么。本章的基础做法先选择完整轮次边界，不要求一开始实现所有切分方式。

摘要也不能只写“之前讨论了配置”。如果旧历史包含“只改主题，端口 3000 不许动”，下面两种摘要就有明显区别：

```text
不足：已经检查过配置。

可用：目标是修改主题，端口 3000 必须保留。
      已确认当前主题为 light，尚未修改文件。
```

检查摘要时，至少对照当前目标、明确约束、已确认结果和未完成工作。把猜测写成事实、把待执行动作写成已经完成，都可能让后续步骤走错。规则检查可以发现遗漏，语义是否准确仍需要验证；摘要失败时保留原记录，不用不可信的新摘要覆盖恢复点。

## 4. 摘要写好了，模型为什么还看到旧消息？

保存压缩点，只改变了存储。内存里的旧消息列表不会自动更新，请求前还要重新组装 Prompt View。

最小关系是：

```text
旧历史 → 摘要
最近原文 → retained_tail
后续消息 → 继续追加

本轮输入 = 最新摘要 + retained_tail + 压缩后的新消息
```

下面用普通文本消息演示组装；摘要内容是给定的示例，不是这段代码自动生成的：

```python
checkpoint = {
    "summary": "目标文件是 config.json，端口 3000 必须保留。",
    "retained_tail": [
        {"role": "user", "content": "主题现在是什么？"},
        {"role": "assistant", "content": "light"},
    ],
}
new_messages = [{"role": "user", "content": "把主题改为 dark"}]

messages = [{
    "role": "assistant",
    "content": "历史摘要：" + checkpoint["summary"],
}]
messages.extend(checkpoint["retained_tail"])
messages.extend(new_messages)

for message in messages:
    print(message["role"], message["content"])
```

输出为：

```text
assistant 历史摘要：目标文件是 config.json，端口 3000 必须保留。
user 主题现在是什么？
assistant light
user 把主题改为 dark
```

这里展示的是会话部分；系统说明和工具定义仍由调用方加入请求。模型接收展开后的消息，不是 checkpoint 的 JSON 外壳。真实工具消息还要保留角色、调用编号和匹配结果。摘要是回顾资料，不能把日志中的恶意文字升级成系统指令。

第二次压缩还必须接住第一份摘要：

```text
第一次：摘要 T1～T5，保留 T6～T8
第二次：摘要“上一份摘要 + T6～T9”，保留 T10～T12
```

如果第二次从 T6 开始，忘了带上旧摘要，T1～T5 的信息就会离开未来输入。反过来，把每一份旧摘要全部重发，也会让压缩失去意义。

这些恢复记录可以追加到 JSONL：一行一个独立 JSON 对象，新事件不覆盖旧事件。也可以存入数据库。存储方式沿用上一课的选择，Prompt View 始终要由程序重新组装。

当前任务进度放进 Summary；经确认、跨会话仍有用的事实才考虑写入 Memory。临时日志、猜测和敏感内容不能因为“马上要压缩”就自动变成长期记忆。

## 5. Prompt 更短，为什么还可能更贵？

部分模型服务会复用相同输入前缀的计算，这叫 **Prompt Cache**。缓存的是计算，不是替应用保管完整会话。

假设前 30,000 Token 原本稳定不变。每轮都改写靠前的历史，可能让后续一大段前缀无法复用。输入虽然少了几百 Token，重新计算的部分反而更多，具体影响取决于服务的缓存和计费规则。[3]

压缩还有摘要请求、等待时间和语义损失。因此不要只比较压缩前后的长度，还要看：

- 回收了多少输入空间；
- 摘要与后续请求增加了多少时间、费用；
- 缓存命中是否变化；
- 关键目标和约束是否仍然保留。

每轮做一点小压缩，可以摊开一次大压缩的停顿，却会更早改写历史、影响稳定前缀；需要根据实际结果选择频率，不能把“越短越好”当成目标。

压缩也可以由模型服务提供，但应用保存的完整会话、长期事实与执行证据仍有独立用途。[4][5]

现在可以把本章接回 Agent Loop：工具输出先受控返回，请求前检查预算；需要压缩时找安全切点，验证并保存摘要，再重新组装输入。完整记录留下，模型每次只看当前需要的内容。

下一课再处理另一种中断：文件已经改完，执行回执却没保存。历史能压缩、能恢复，还不等于外部动作可以放心重做。
