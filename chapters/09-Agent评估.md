# 第 9 课：Agent Evaluation——任务验收与回归门禁

一个已经能修改文件的 Agent，换成更便宜的模型后，还能放心使用吗？

你让它修改一次配置。文件改对了，回答也正常，看起来可以替换。随后另一项任务要求“修改主题，保留端口和调试开关”，它却顺手重写了整个配置，把调试开关删掉了。一次演示没有暴露这个区别。

到第 8 课，我们已经能用运行记录追踪失败：Model 看到了什么，Tool 做了什么，哪一步停了下来。现在要解决的是修改系统时的判断：**哪些任务变好了，哪些旧能力退步了，现有证据是否支持保留这次改动？**

本章继续使用前几课的 Workspace Agent。目标是能为它设计一套小型评测，读懂结果，再把需要守住的规则接到发布流程中。

## 1. 评估的是哪一个系统？

给模型输入一句话、检查回答，是一种评估。让 Agent 带着上下文调用工具、修改文件、处理中断，再检查任务结果，也是一种评估。后者的表现由模型和运行时共同决定：

```text
被评估的 Agent 版本
= Model + Prompt + Context + Harness + Tool + 执行环境
```

修改其中任意一项，都可能改变任务表现。模型没换，压缩历史时丢掉“不要改端口”的要求，结果也会变；Prompt 没换，工具返回内容被截短，模型同样可能判断错误。

把这些表现变成有依据的检查与测量，就是 **Agent Evaluation（Agent 评估）**。在开发阶段，可以先记住这句：

> 固定试卷 + 明确成功条件 + 重复运行 + 比较结果。

这里的“明确”指要求可以判断，不要求所有正确答案字字相同。Evaluation 既可用于发现新能力，也可用于保护旧能力：

| 用途 | 要回答的问题 | 题目怎样选择 |
| --- | --- | --- |
| Capability Evaluation，能力评估 | 想让 Agent 学会的事情，做到了多少？ | 选当前仍有困难、但需求明确且可完成的任务 |
| Regression Evaluation，回归评估 | 应用已经依赖的行为，改完以后还成立吗？ | 保留稳定能力和曾经出过故障的关键任务 |

能力评估允许暴露大量失败；回归评估关注已有保证的退步。同一道题稳定通过、成为应用承诺后，可以从改进目标转为长期回归检查。这一区分来自 [Anthropic 的 Agent Eval 指南](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)。

前几课的单元测试和故障注入仍然有用：它们验证切分边界、状态恢复等确定规则。真实模型评测再回答模型会不会选对工具、理解约束并完成任务。两类证据覆盖不同的失败。

## 2. 先选题，再决定跑多少次

一份输入、任务说明和验收条件，构成一个 **Task（测试任务）**；实际执行一遍，叫一次 **Trial（尝试）**。一次 Trial 里面可以有多轮模型请求、多个工具调用。

同一道 CSV 汇总题做十次，观察的是这道题能否稳定完成。十道不同输入的题各做一次，观察的是能否处理这些不同情况。题目覆盖和重复次数不能相互代替。

选题时，先列出准备修改的系统已经承担哪些职责。对当前 Workspace Agent，可以从下面几类开始：

| 要检查的能力 | 一个具体案例 | 应留下什么证据 |
| --- | --- | --- |
| 正确修改 | 把主题改成 dark，端口保持 3000 | 修改前后配置及完整运行结果 |
| 保留非目标数据 | 配置多一个 debug 字段，仍只改主题 | 目标字段正确，其他字段和值未变 |
| 根据输入计算 | 汇总 CSV，换一份数量后答案也相应变化 | 原始数据、实际总数 |
| Context 完整性 | 压缩历史时不拆散 Tool Call 和 Tool Result | Prompt View 中配对消息仍完整 |
| 恢复与防重 | 副作用后中断，再次启动不盲目执行 | Ledger 恢复状态和实际执行次数 |
| 权限约束 | 用户拒绝写入后，执行器不产生写操作 | 审批结果、执行次数和文件状态 |

前三类适合调用真实模型完成任务；后三类已有确定性的运行时检查。它们都能保护系统，但不能把所有通过数加起来，称为“模型成功率”。

最初的题目可来自日常验收、已知故障和高风险约束。再为关键规则配上反方向的案例：既检查禁止写入时能否拦住，也检查允许写入时能否完成。否则，一个永远拒绝的 Agent 也可能在只有拒绝题的试卷上获得满分。

用于反复调试的题会越来越熟悉。另留少量没有参与调试的同类任务，检查改动是否只适用于熟悉样例。发现的新故障进入下一版题集，题集也要记录版本。线上失败回到离线评测集的工作流，可见 [LangSmith Evaluation](https://docs.langchain.com/langsmith/evaluation)。

一开始不必搭建大平台。先让题表中的每一行都能回答：“这道题失败，会改变我对哪项能力的判断？”

## 3. 怎样把要求写成可信的评分？

选择 CSV 作为最小示例。题目必须把输出要求说全：

> 读取 items.csv，将 quantity 列的非负整数相加。把结果写入 summary.json，输出必须是仅包含整数 total_quantity 字段的 JSON 对象。保留 items.csv 原样，完成后如实回答。

```csv
item,quantity
apple,2
banana,3
pear,7
```

满足这份契约的文件是 `{"total_quantity":12}`。字段顺序、空格和换行不影响这里的含义；缺文件、算错、写成字符串 `"12"`，则没有满足约定。若题目没有要求“仅有一个字段”，评分器就不应擅自因附带一个合法说明字段而扣分。

负责判断的函数或规则叫 **Grader（评分器）**。它先要有可信的依据。

如果标准答案取自 Agent 运行后的 CSV，Agent 把输入和结果一起改掉，两边仍可能相等。因此运行前保存原始快照，评分时用快照计算答案，并比较工作区里的输入是否未变：

```text
运行前的原始 CSV ---> 计算预期总数
         |                 |
         |                 +-- 对照 summary.json 的实际总数
         +-------------------- 对照 items.csv 是否未变
```

本练习的 `grade_csv_total()` 使用 `csv.DictReader` 计算原始总数。输入改为数量 10 和 20，答案便是 30，无须修改评分逻辑。

原始快照还必须受到实际权限保护。当前运行器只允许读取指定输入、写入指定输出，没有开放 Shell；快照位于这些入口不可访问的位置。以后接入 Bash 或远程工具，需要重新检查保护边界。把文件放到工作区外，本身不构成 Sandbox。

一个任务通常有几个不同维度的判断：

| 维度 | CSV 案例中的检查 | 适合的方式 |
| --- | --- | --- |
| 结果 | 总数正确、输出结构符合约定 | 解析文件并计算 |
| 行为约束 | 原始输入没有被改动 | 对照快照；必要时核对执行记录 |
| 用户交付 | 正常结束，回答与实际产物一致 | 运行状态加回答核验 |
| 代价 | 时间、Token、请求和工具次数 | 运行器记录并按预定指标汇总 |

当前文件评分器覆盖前两项；运行器另记结束状态，尚未自动判断自然语言回答是否与产物完全一致。输出的每个字段，都应有可指认的证据，不能把没有实现的检查算进总成绩。

检查过程时，也不要把作者习惯的步骤强加给模型。两种工具顺序可能都能合法完成任务；只对确有要求的次序设约束，例如审批必须在执行前。结果、单步决策和整段行为可以分别评估，[LangSmith 的 Agent 评估说明](https://docs.langchain.com/langsmith/evaluation-approaches)讨论了这些方式及固定路径匹配的局限。

文章总结等开放任务很难靠唯一字符串评分。这时可以让人工或 LLM Judge 按具体标准判断，例如“关键结论是否有来源支持”。先用人工标注的正确、错误和边界样例检查 Judge 的判断，重点阅读分歧案例，再决定是否采用它的分数。代码评分、模型评分和自定义评分也可以组合使用；[Inspect Scorers](https://inspect.aisi.org.uk/scorers.html)提供了相应接口。

评分器自己也需要验证。给它一份已知正确答案、一份明确错误答案，再给一份只改变空格的等价答案，观察是否分别通过、失败、通过。没有抛异常的评分器，也可能一直判错。

## 4. 怎样运行，才不会把环境问题算成能力？

评测也需要一段程序来组织任务：准备环境、启动 Agent、保留证据、调用 Grader。这段组织评测的代码常叫 **Evaluation Harness**。它在被测 Agent 外面；前面课程的 Agent Harness 则负责内部的模型与工具循环。

```text
Evaluation Harness
  1. 准备独立工作区、原始快照和任务说明
  2. 运行被测 Agent
       Model <-> Agent Harness <-> Tool / Environment
  3. 保存产物、会话及运行结果
  4. 调用 Grader，生成本次 Trial 报告
```

每次 Trial 都重新准备初始文件与会话，防止上一轮产物、历史消息或缓存影响下一轮。任务运行中的状态可以持续；不同独立尝试之间不能误共享状态。

本课现有文件正好对应这些职责：

| 文件 | 作用 |
| --- | --- |
| `run_trial.py` | 准备工作区，调用综合实践的 Agent，保存报告 |
| `starter.py` | 提供配置与 CSV 评分器，以及评分器自检 |
| `compare_runs.py` | 读取已保存报告，比较条件与成绩 |

`--self-check` 使用预设模型回复检查程序行为；`--live` 才调用实际模型。二者都可能走真实文件工具，但前者不能证明模型会自行作出那些选择。正式 Trace/Span 不是开展结果评测的前提：本次运行保存的是会话、Ledger 和报告，第 8 课的 Tracing 可在需要更细诊断时接入。

评测中的“离线”通常指在测试集上进行开发期验证，并不意味着断网。离线评测可以调用云端模型；“不调用模型、只读历史报告”则是本课比较命令的具体行为。

报告必须区分三种产物评分：

```text
passed  已完成评分，产物满足本题条件
failed  已完成评分，产物不满足本题条件
error   评分未能完成，不能据此判断产物合格
```

损坏的输出 JSON 是产物失败；评分器自己的 `NameError`、可信原始数据丢失，是评分故障。其他独立答卷可以继续评分。若只是修好评分实现、原证据仍完整且成功标准未变，直接补评原产物；修订了标准，则旧版和新版都要按新标准评价。

Agent 的运行状态单独保存。例如文件已经正确，但模型在 Final 前中断：

```text
产物评分 passed + 运行 error
```

本练习仅将“运行 completed 且产物 passed”计入完整成功。它不要求把文件、模型调用和回答包进一个事务，而是保留两个判断，方便区分“做错了”与“做对后没有完成交付”。网络异常属于本次运行记录，评分代码异常属于测量问题，二者不能互相替代。

## 5. 怎样比较版本，才能知道改动有没有收益？

先写清本轮要回答的问题。研究 Prompt 时，模型、工具和预算等条件保持一致；研究换模型时，模型就是允许变化的对象。比较整体方案，也可以同时改变多项配置，但结论只能针对整体方案，不能把收益全部归给某一项。

同一道题的相同初始状态、相同验收规则，是可解释比较的重要基础。还应记录服务、环境、预算和实际版本。基础设施本身会影响 Agent 分数；Anthropic 的研究展示了资源限制如何改变失败率和可完成的解法。[基础设施噪声研究](https://www.anthropic.com/engineering/infrastructure-noise)

本练习为了控制规模，让两个 Prompt 各做三次相同任务，并要求 Trial 数一致。等量便于对照，不是通用统计定律；不同样本量也可以比较，需要合适的方法并报告不确定性。三个样本无法因为“3/3”就证明长期可靠，相关比例比较方法见 [NIST](https://www.itl.nist.gov/div898/software/dataplot/refman2/auxillar/diffprop.htm)。

归档实验只增加了一条“写入后读回核对”的 Prompt 要求。两版都使用 `mimo-v2.5`、同一 CSV、工具范围、评分器，以及每次最多四次模型请求：

| 版本 | 产物通过 | 完整运行成功 |
| --- | --- | --- |
| baseline | 3/3 | 3/3 |
| verify-output | 2/3 | 0/3 |

前两次候选运行的会话都停在：

```text
模型请求 1 -> 读取 items.csv
模型请求 2 -> 写入 summary.json
模型请求 3 -> 读取 summary.json
模型请求 4 -> 再次读取 items.csv
请求预算用完，无法再请求模型生成 Final
```

这是请求次数耗尽，不是 Token 上下文已满。第三次记录 `APIConnectionError`，不能据此归罪于 Prompt。前两次的重复检查是值得验证的原因假设，少量样本不能给出普遍结论。

分析时要逐类看任务、逐次看失败。新增一个简单任务，可能让平均成功率上涨，却掩盖某项关键能力的下降。耗时也要和完成情况一起解释：这次候选的平均耗时更短，其中包含提前失败，不能据此宣布更高效。Tool 次数不是费用；未记录 Token 用量与价格时，就不能声称已经量出了成本收益。

接下来可以保留原始记录，针对重复检查修改 Prompt，再在原任务和未参与调试的同类任务上验证。若四次请求不足以代表实际产品预算，也可以设计新实验调整预算，但必须重跑两版并注明条件改变。不能悄悄把旧成绩放进新条件下作比较。

## 6. 怎样把评估结果变成回归门禁？

回归的意思是：应用以前依赖的行为，在改动后退步了。修复代码时，既要检查原失败测试现在能否通过，也要确认原通过测试仍然通过。SWE-bench 的评分实现就同时使用 `FAIL_TO_PASS` 与 `PASS_TO_PASS` 判断修复是否成立。[SWE-bench 评分实现](https://www.swebench.com/SWE-bench/api/harness/#swebench.harness.grading.get_resolution_status)

**Regression Gate（回归门禁）是利用这些证据决定候选改动能否继续进入发布的规则。**如果 Evaluation 是考试，门禁就是发布门口的门卫：成绩单提供证据，门卫按提前确定的规则决定放行。

规则应按性质分别制定：

| 规则 | 处理方式 |
| --- | --- |
| 不得未经批准产生写操作 | 硬约束，观察到违例就阻止放行 |
| 常见任务的完成质量 | 按任务类别和预定标准比较，考虑重复运行的波动 |
| 延迟、Token 和费用 | 按业务预算权衡，不能靠提前失败制造好看指标 |
| 评分故障、缺失记录或版本对不上 | 证据不足，先修复或补齐验证 |

“没有观察到越权”不证明永远安全；Sandbox 和执行器继续负责强制边界，评测负责检查保证是否失效。也不能用整体质量提升抵消一条硬约束的失败。

本地 `release_gate()` 是最小教学实现：先确认报告可比较，再要求候选的这道固定题每次都正常完成且产物通过。它不包含通用统计检验，也没有覆盖整个 Agent 的安全和质量要求。运行已有证据：

```bash
python -B exercises/lesson-09-evaluation/compare_runs.py \
  --baseline exercises/lesson-09-evaluation/evidence/baseline.json \
  --candidate exercises/lesson-09-evaluation/evidence/candidate.json \
  --gate
```

报告中的两个状态会同时出现：

```text
comparison.status = comparable   这些记录满足本练习的比较条件
status = blocked                 候选未达到本例的放行规则
```

命令以退出码 2 结束。它提供阻断信号；只有流水线接收并遵守这个信号，才能真正阻止合并或部署。Promptfoo 的 CI/CD 文档展示了用评测结果执行 Quality Gate 的方式。[Promptfoo：CI/CD 与质量门禁](https://www.promptfoo.dev/docs/integrations/ci-cd/)

生产使用还需要把报告与待发布版本绑定：

```text
固定候选代码、实际 Prompt、模型配置、题集和评分规则
-> 对这个候选运行检查并保存证据
-> 门禁核对成绩及版本身份
-> 只发布刚才通过检查的同一份候选产物
```

只记录 Git Commit 不够：未提交的 Prompt、外部模型配置也可能变化。当前报告保存了若干内容指纹，但比较器仅核对报告内部条件，未校验当前工作树，也没有接入发布流程。归档 CSV 成绩用于演示判断逻辑，不能给后来改过的代码发“通行证”。

这些历史成绩是在本次门禁规则形成前产生的。用它们检验规则能否拦住已知问题，属于规则演示；新的正式实验应先确定标准。出现网络失败时，门禁可以等待补充证据，但这并不等于已经证明候选代码有缺陷。

## 7. 让评估进入日常开发

一个有用的循环是：遇到真实失败，写清任务和成功条件；验证评分可信，再改 Agent；检查目标问题是否改善、旧能力是否保留，最后按证据决定是否发布。发布后的真实失败，再补进后续题集。

本课配套的[约 30 分钟综合实践](../exercises/lesson-09-evaluation/README.md)要求交付一张小题表和一份版本判断。它复用已有评分器、运行时检查与真实报告，重点在选题、辨认证据和解释结论。

读完后遇到一次 Context 或工具改动，你应当能指出受影响的能力、选择相应任务、识别评分的盲区，并说明哪些结果还不能支持放行。这比背下 `passed`、`failed`、`error` 更接近实际开发工作。

评估暴露的问题，可能需要修改 Prompt、工具描述、Context 或预算，也可能需要重新安排流程。下一课讨论 Workflow、Routing 与长任务时，这套任务和检查可以继续使用，帮助判断新增编排是否解决了原来的问题。
