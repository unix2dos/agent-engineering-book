# 第 9 课：Agent Evaluation——任务验收与回归门禁

假设你给 Agent 换了个更便宜的模型。第一次，它改对了配置；第二次，它改了主题，也改了你要求保留的端口。换个皮肤，附赠一次端口迁移。

一次演示很难暴露这些差别。你需要一组任务，检查新版完成了什么、破坏了什么，再决定是否替换。固定任务和成功条件，重复运行并比较结果，这就是 **Agent Evaluation（Agent 评估）**。

上一课的运行记录帮助解释“哪里出了问题”。这一课要让这些发现支持一个决定：这次改动是否值得保留？

## 1. 先说清什么算成功

任务是把配置主题从 light 改成 dark，其他字段保持不变。

```text
修改前：{"theme":"light","port":3000}
正确结果：{"theme":"dark","port":3000}
实际结果：{"theme":"dark","port":8080}
```

主题改对了，端口却变了，所以任务失败。Agent 回复“已经完成”不能代替这项检查。

负责检查结果的程序叫 **Grader（评分器）**。这道题可以这样比较：

```python
import json

before = json.loads('{"theme":"light","port":3000}')
actual = json.loads('{"theme":"dark","port":8080}')

expected = before.copy()
expected["theme"] = "dark"

print(actual == expected)
```

输出是 `False`：实际配置不等于预期配置。解析 JSON 后，空格和字段顺序不影响比较。完整评分器还要处理文件缺失、格式错误和字段类型；它不能额外检查题目从未要求的限制。

评分依据要在 Agent 执行前保留，并放在它无权修改的位置。否则，它可能把输入和答案一起改掉，再让两者“对上”。保护来自执行权限，单独把文件移到工作区外并不够。

换一种任务，就换一种检查。计算题可以从原始数据算出答案；修复代码可以运行受保护的测试；文章总结则可能需要人工或模型按明确标准判断。让另一个模型评分时，先用人工确认过的样例校准它，再检查双方判断不一致的地方。[1][2]

评分器自身也要验收：正确答案应通过，明确错误应失败，只改变空格的等价答案仍应通过。程序没有报错，不等于它判得正确。

## 2. 选一组能反映能力的题

一个有明确输入和成功条件的测试任务，叫 **Task**。实际做一遍，叫一次 **Trial**。同一道题做十次，检查稳定性；换十道题，检查它能应付哪些情况。

先从日常任务、已知故障和重要约束中选题：

| 想检查什么 | 可以怎样出题 |
| --- | --- |
| 保留非目标数据 | 端口改成 3000，再多放一个 debug 字段，仍要求只改主题 |
| 保留历史约束 | 先要求“不要改端口”，几轮对话后再提出修改任务 |
| 正确使用权限 | 一题允许写入，另一题拒绝写入，分别检查实际动作 |
| 根据输入计算 | 换一份 CSV 数量，检查总数是否跟着改变 |

只出拒绝题，一个永远拒绝的 Agent 也可能全对。只出已经反复调试的题，又可能看不出它在陌生输入上的问题。应保留少量未参与调试的同类任务。

题目还有两种用途：希望 Agent 学会的新任务用于**能力评估**；应用已经依赖的行为用于**回归评估**。前者寻找改进空间，后者检查旧能力是否退步。稳定的新能力成为应用承诺后，也可以进入回归集。[1]

前几课的确定性检查继续保留。例如，检查压缩切点不拆散工具调用与结果，验证的是运行时规则；让真实模型在压缩后完成任务，才能进一步观察它是否仍理解用户要求。两类通过数不能混加成一个“模型成功率”。

## 3. 每次从同一起点开始，分别记下结果

每次 Trial 都要重新准备初始文件和会话。否则，上一轮已经改好的文件留在那里，下一轮即使什么都没做，也可能被判成功。

整个评测程序只需把几件事接起来：

```text
准备原始输入 → 运行 Agent → 保存实际结果 → 按规则评分
```

下面两份示例配置已经解析为字典。第一份改对了，第二份误改端口；逐份评分时使用同一份标准答案：

```python
expected = {"theme": "dark", "port": 3000}
outputs = [
    {"theme": "dark", "port": 3000},
    {"theme": "dark", "port": 8080},
]

grades = []
for output in outputs:
    if output == expected:
        grades.append("passed")
    else:
        grades.append("failed")

print(grades)
```

输出为：

```text
['passed', 'failed']
```

循环每读一份配置，就把判断加入 `grades` 列表。这段只演示结果评分；真正的 Agent 运行发生在此之前。格式损坏、自身异常等情况，再按下面的规则分别记录。

评分时保留三种情况：

| 评分 | 含义 | 例子 |
| --- | --- | --- |
| passed | 已经检查，结果符合要求 | 主题正确，其他配置未变 |
| failed | 已经检查，结果不符合要求 | 端口被删除，或输出 JSON 损坏 |
| error | 评分没完成，成绩未知 | 评分代码出错，或原始题目数据丢失 |

评分器出错，修好后可以对原产物补评，不必重跑 Agent；前提是证据完整，成功条件没有改变。若修改了标准，两个版本都要按新标准评价。

运行状态还要单独记录。文件可能已经写对，模型却在最终回答前中断：

```text
文件评分 passed，运行状态 error
```

这道题要求正常结束并交付结果，因此它不能算完整成功。分开记录，可以看出失败发生在做任务时，还是做对以后。若最终回答也是验收目标，还要核对它是否与实际产物一致。

预设模型回复可以验证程序在某种情况下怎样处理，不能证明真实模型会作出那些选择。评估也不以正式 Trace 为前提；文件、会话和执行记录可以先提供证据。开发期的“离线评测”仍可能调用云端模型，“离线”不等于断网。[3]

## 4. 新版更快，为什么仍不值得替换？

先确定本轮研究什么。比较 Prompt 时，保持模型、题目和预算相同；比较模型时，模型就是要改变的变量。多项配置一起改变，也可以比较整体方案，但不能把收益全部归给其中一项。

下面是一组真实 CSV 实验。输入的商品数量为 2、3、7；任务要求计算总数并写入 JSON，保留原始 CSV 并正常结束。正确总数为 12。两版使用同一模型 mimo-v2.5，各做三次，每次最多发起四次模型请求：

| 版本 | 文件正确 | 完整成功 |
| --- | --- | --- |
| 原版 | 3/3 | 3/3 |
| 增加“写完后读回核对”的新版 | 2/3 | 0/3 |

新版前两次都写对了文件，却走到了同一个结尾：

```text
第 1 次请求：读取输入
第 2 次请求：写入结果
第 3 次请求：读回结果
第 4 次请求：再次读取输入
请求次数用完，无法继续生成最终回答
```

文件写对了，Agent 却连一句“做完了”的请求额度都没留下。

耗尽的是请求次数，不是 Token 上下文。第三次则是 API 连接失败，不能归罪于 Prompt。

新版平均耗时更短，其中包含提前失败，所以不能据此宣布更高效。应先检查重复读取是否稳定出现，再调整方案验证。运行记录支持原因分析；它们不会自动把相关现象变成因果结论。

比较时要按任务类别看结果，避免平均分掩盖某项关键能力的下降。还要结合完成质量看时间和费用，不能把工具次数直接当作成本。

三次全对也不能证明长期可靠。这里用相同次数便于对照；不同样本量仍可比较，但需要处理统计不确定性。环境、资源和预算也会影响结果，必须随报告记录。[4][5]

若调整了预算，就应按新条件重新运行两个版本。不能看见新版失败后，临时放宽要求来让旧成绩过关。

## 5. 把不能退步的行为变成发布门禁

**回归门禁（Regression Gate）根据回归评估的证据，决定候选改动能否继续发布**。如果评估是考试，门禁就是发布门口的门卫。

“修好了新问题”与“保住了旧行为”需要同时检查。SWE-bench 评估代码修复时，就分别检查原来失败的测试能否通过，以及原来通过的测试是否仍然通过。[6]

门禁规则要在运行前确定：

- 不得未经批准产生写操作：观察到违例就阻止放行。
- 常见任务的质量：按预定标准比较，并考虑多次运行的波动。
- 时间和费用：结合完成质量与业务预算判断。
- 评分故障、记录缺失、版本对不上：先补齐证据。

安全违例不能靠其他题的高分抵消。测试中没观察到违例，也不证明永远安全，执行器和 Sandbox 仍要负责强制边界。

把放行规则写进程序，就能得到明确的通过或拦截。下面用三份假设报告演示“固定题全部完整通过”的规则；`run` 是运行状态，`grade` 是产物评分：

```python
reports = [
    {"run": "completed", "grade": "passed"},
    {"run": "completed", "grade": "failed"},
    {"run": "error", "grade": "passed"},
]

can_release = len(reports) > 0
for report in reports:
    if report["run"] != "completed" or report["grade"] != "passed":
        can_release = False

if can_release:
    print("通过")
else:
    print("拦截")
```

输出为 `拦截`。第二份产物失败，第三份虽写对了文件，运行却没结束，任何一种都足以拦住。`len(reports) > 0` 还保证没有成绩时不能放行。

这段只展示判定核心；真实门禁还要核对题目、版本和证据。自然语言质量等有波动的指标，仍按前面约定的标准比较。

对刚才的 CSV 实验，如果规则要求每次都完整完成，新版就会被拦住。网络错误不能证明 Prompt 有缺陷，但这份记录也没有提供成功验证。能比较两份报告，和候选满足放行条件，是两个判断。

门禁程序返回失败，只是发出了信号。发布流程必须遵守这个信号，并且发布的代码、实际 Prompt 和模型配置要与受测版本一致。拿旧报告给后来改过的系统背书，没有意义。[7]

这组实测只覆盖 CSV 任务，没有验证生产发布流程。配套材料保留了运行条件和原始报告。

以后修改 Context、工具或模型时，先选出会受影响的任务。运行、检查、比较，再决定保留或调整；真实使用中发现的新故障进入回归集。下一课讨论 Workflow、Routing 和长任务时，这套检查可以继续检验新增流程是否解决了原来的问题。
