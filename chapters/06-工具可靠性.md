# 第 6 课：Tool Reliability——幂等、Ledger 与故障恢复

假设你的支付 Agent 正在处理一笔退款。网络请求已经成功打到了第三方支付网关，银行账户扣款完成，但就在程序准备把“退款凭证”写入本地数据库的前一毫秒，机房保险丝烧了。

系统重启后，Agent 望着一片空白的本地记录，陷入了系统论中最凶险的境地：这笔钱到底是扣了，还是没扣？

如果当成失败直接重跑，用户可能喜提两倍退款；如果当成没发生直接忽略，财务月底对账会提着扳手来找你。在带外部副作用的世界里，最致命的永远不是明确的报错，而是“动作已经发生，但执行者失忆了”。

为了看清这类故障，我们先把它缩减到一个最小的可运行场景：Agent 收到任务把 `answer.txt` 的完整内容改成 `done`。

正常顺序很简单：

```text
Model 请求 write_file
→ Harness 写文件
→ 把 Tool Result 交还 Model
→ Model 给出 Assistant Final
```

最麻烦的故障发生在中间：文件已经写完，程序却在保存 Tool Result 前崩溃。

重启后，Session 里只剩一张没有回执的 Tool Call。Agent 无法只靠它判断：工具根本没运行，还是已经运行但结果丢了。

这不是普通失败：

```text
failed  = 已经确认工具失败
unknown = 无法确认副作用是否发生
```

如果把 `unknown` 当成失败直接重跑，邮件可能发两次，付款可能扣两次，`echo x >> audit.log` 也可能追加两行。这一课要做的，就是把这段空白变成可以检查、可以恢复的记录。

## 1. Transcript 为什么还不够？

Transcript 保存 Model 与 Tool 之间的对话：

```text
User
Assistant Tool Call
Tool Result
Assistant Final
```

它适合让 Model 继续说话，却没有详细记录工具何时获准、何时开始，以及执行到哪一步崩溃。

因此综合实践在同一份 JSONL 中加入另一类记录：

```text
type=message         给 Model 使用的会话消息
type=compaction      上下文压缩恢复点
type=tool_execution  给 Harness 查账的执行流水
```

这条工具执行流水叫 Tool Execution Ledger，后面简称 Ledger。它不会进入 Prompt。`build_prompt_view()` 只挑出 `type=message`，所以 Model 不会看到内部的 `approved`、`running` 和重试记录。

最短的区别是：

```text
Transcript 记录 Model 经历了什么
Ledger     记录 Tool 实际走到了哪一步
```

## 2. 为什么 running 必须在执行前写盘？

可靠执行首先要求固定顺序：

```text
Assistant Tool Call 已保存
→ 用户拒绝：写 rejected，不执行 Tool
→ 用户批准：写 approved
→ 写 running，并确保落盘
→ 执行 Tool
→ 写 succeeded / failed 和 result
→ 写 Tool Result Message
→ Model 生成 Assistant Final
```

`running` 必须先于副作用。如果先执行文件写入，再保存 `running`，程序可能在两者之间崩溃。磁盘还停在 `approved`，恢复代码就可能误以为工具从未开始。

终态与 `result` 也要放在同一条 Ledger Entry 中。正常情况下只会出现两种结果：

```text
终态和 result 一起落盘
或者二者都没落盘，最后状态仍是 running
```

如果 Ledger 已经保存 `succeeded + result`，但 Tool Result Message 尚未写入，恢复程序只需重放结果，不必再次执行 Tool。

下面是一次正常写文件留下的最小 JSONL。为了看清顺序，省略了长 Hash：

```jsonl
{"type":"message","message":{"role":"user","content":"把 answer.txt 写成 done"}}
{"type":"message","message":{"role":"assistant","tool_calls":[{"id":"call_1","function":{"name":"write_file","arguments":"{\"path\":\"answer.txt\",\"content\":\"done\"}"}}]}}
{"type":"tool_execution","execution_id":"exec_1","tool_call_id":"call_1","status":"approved"}
{"type":"tool_execution","execution_id":"exec_1","tool_call_id":"call_1","status":"running"}
{"type":"tool_execution","execution_id":"exec_1","tool_call_id":"call_1","status":"succeeded","result":{"path":"answer.txt","bytes_written":4}}
{"type":"message","message":{"role":"tool","tool_call_id":"call_1","content":"{\"status\":\"succeeded\"}"}}
{"type":"message","message":{"role":"assistant","content":"文件已经写好"}}
```

磁盘有七条 Entry，Model 仍只看到四条 Message。Ledger 留在磁盘供恢复程序读取。

## 3. 为什么一次 Tool Call 需要三个 ID？

崩溃恢复时，有三件容易混在一起的事：Model 发出的申请、Harness 的执行尝试，以及多次尝试是否属于同一个逻辑动作。

| ID | 回答的问题 | 何时变化 |
| --- | --- | --- |
| `tool_call_id` | Tool Result 回答哪张 Model 申请？ | Model 产生新 Tool Call 时 |
| `execution_id` | 这是第几次真实执行尝试？ | 每次尝试或重试时 |
| `idempotency_key` | 多次尝试是否在完成同一个调用？ | 逻辑调用变化时 |

同一 Tool Call 重试两次时：

```text
第一次：tool_call_id=call_1  execution_id=exec_1
第二次：tool_call_id=call_1  execution_id=exec_2

两次共享：idempotency_key=write_file:call_1
```

`tool_call_id` 不变，因为最后仍要给原申请补回执。`execution_id` 必须变化，否则 Ledger 无法区分两次尝试。

参数 Hash 又解决另一件事。综合实践先把 JSON 字段排序，再计算 `arguments_sha256`：

```text
同一个 Key + 相同参数 Hash → 同一个逻辑调用
同一个 Key + 不同参数 Hash → 身份冲突，停止处理
```

Hash 只负责发现参数变化，不会阻止重复执行。真正的防重必须由执行器、数据库唯一约束或外部 API 按 `idempotency_key` 实现。

给任意 Bash 命令附上一个 Key 没有用。`echo sent >> audit.log` 不会读取它，每运行一次仍会追加一行。

## 4. 数据库怎样把幂等要求变成硬约束？

假设两个 Worker 同时收到相同的 `idempotency_key`。如果应用先查询、再决定是否写入，两边可能同时看到“还不存在”：

```text
Worker A：查询，不存在
Worker B：查询，也不存在
Worker A：准备执行
Worker B：也准备执行
```

两次查询都没有读错，只是它们看见了同一个旧状态。真正的防重必须发生在写入那一刻。例如把 `idempotency_key` 设为 SQLite 主键，数据库便只允许一条相同 Key 的记录落库：

```sql
INSERT INTO tool_operations(idempotency_key, arguments_sha256)
VALUES (?, ?)
ON CONFLICT(idempotency_key) DO NOTHING
```

第一次插入成功，调用取得执行资格。相同 Key 和相同参数再次出现，说明它是同一逻辑调用的重复请求；相同 Key 却带着不同参数，则是身份冲突，必须停止。

为了同时保留历史和快速恢复，程序还可能维护两张表：

```text
execution_events              execution_state
保存每次状态变化               保存每次执行的最新状态

exec_1 running                exec_1 unknown
exec_1 unknown                exec_2 succeeded
exec_2 unknown
exec_2 succeeded
```

右边这张 `execution_state` 是从完整事件提前算出的当前答案，数据库里常叫物化状态。它让程序不用每次启动都从第一条事件重算，但也让一次写入变成两步：追加事件，同时更新当前状态。

两步必须放进同一个事务。否则程序可能已经写下 `unknown` 事件，当前状态却还停在 `running`：

```python
with database:
    database.execute("INSERT INTO execution_events ...")
    database.execute("INSERT INTO execution_state ... ON CONFLICT ...")
```

事务保证两步一起成功或一起撤回。若两张表发生冲突，应把完整事件当作事实来源，重新生成物化状态。

这不表示每个 Agent 都要使用 SQLite。单进程、低频恢复的 JSONL Ledger 完全可以工作；当系统开始频繁按状态查询、需要多项写入一起成功，或者需要数据库唯一约束裁决并发时，SQLite 才真正省事。WAL 可以减少同一台机器上读写互相等待，但不会把 SQLite 变成多主机、多 Writer 数据库。[SQLite WAL](https://www.sqlite.org/wal.html)

[SQLite 专项练习](../exercises/session-storage-sqlite/README.md)会分别制造物化状态不一致、事务中途失败和重复 Key 三种故障。练习的是数据库保证，不是另一套 Agent 架构。

## 5. 重启后怎样把旧 Turn 修完整？

第五关把恢复拆成四步，每一步只回答一个问题。

第一步，扫描每个 `execution_id` 的最后状态。旧进程留下的 `running` 不能猜成失败，只能追加为 `unknown`：

```text
approved → running → unknown
```

旧的 `running` 不会被覆盖。Ledger 保留完整变化，内存字典只用后一条覆盖前一条，方便程序读取当前状态。

第二步，找出孤立 Tool Call。`pending_tool_calls()` 看到 Assistant Tool Call 就把 ID 放进待处理集合，看到相同 ID 的 Tool Result 就删除。最后留下的，都是只有申请、没有回执的调用。

第三步，给孤立调用补 Tool Result：

```text
rejected
→ 重建拒绝回执

succeeded / failed，并且 Ledger 有 result
→ 重放已保存结果，不执行 Tool

unknown
→ 返回“不确定”回执，不执行 Tool

没有 Ledger、参数 Hash 不一致、终态没有 result
→ 停止恢复，不能编造结果
```

补写的是 `role=tool` Message，不是另一条 Ledger Entry。前者修复 Model 协议，后者只负责内部查账。

第四步，把修复后的消息重新交给 Model。此时 Prompt 是：

```text
User → Assistant Tool Call → Tool Result
```

最后一条必须是 `role=tool`，因为下一位该说话的是 Model。恢复代码不能先追加新的 User Message；它要继续旧 Turn，直到出现 Assistant Final。

```text
5B 修复 Ledger 状态
→ 5C 修复 Tool Call / Tool Result 配对
→ 5D 让 Model 完成原来的 Turn
```

## 6. unknown 到底能不能重试？

状态名不能决定重试，Tool 的行为才能。

`read_file` 没有副作用，重新读取通常没问题。任意 `run_bash` 可能发请求、删文件或追加日志，看到 `unknown` 不能直接重跑。

完整覆盖写入 `write_file(path, content)` 看起来天然幂等：重复设置相同内容，最终文件一样。但文件可能在崩溃后被用户或另一个进程修改。此时自动覆盖，会抹掉新修改。

综合实践采取更保守的做法：先对账，不重试。

```text
目标文件 Byte 与原请求 content 完全相同
→ 只能证明目标状态已满足
→ 不重新写文件
→ 在原 execution_id 后追加 succeeded
→ result 标记 reconciled=true

文件不存在或内容不同
→ 保持 unknown
→ 交给用户或更权威的外部查询处理
```

旧的 `unknown` 仍留在 Ledger。新的 `succeeded` 表示逻辑请求的目标已经满足，不证明旧进程究竟写了几次。

支付、发信和部署工具需要更强的证据：使用原幂等 Key 查询下游 API，取得能归属于本次请求的订单号或回执。没有权威回执时，保持 `unknown` 比猜测安全。

## 7. 开源项目怎样处理这些边界？

不同项目使用的状态名不一样，但真正可靠的实现都不会只看一个 `completed` 字段。

DeepSeek Harness 在执行前记录 `tool/call`，经过策略、审批、Guard 和执行后，再提交单一 `tool/result`。并列 Tool 可以同时执行，但模型历史仍按原调用顺序收到全部结果。[Tool Execution Pipeline](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/docs/tool-execution-pipeline.zh.md)

OpenClaw 的 Incomplete Turn Recovery 会检查本批调用是否都有匹配 Result，以及是否存在潜在副作用。已经完成的 Tool 不能只因为缺少可见 Final 就被重复执行。[OpenClaw Recovery](https://github.com/openclaw/openclaw/blob/1fb3e0ca33847b5827a21cf5cb132d3f90ff49ad/src/agents/embedded-agent-runner/run/incomplete-turn-recovery.ts)

Hermes 明确列出无副作用工具；未知工具、插件和 MCP 工具默认按“可能有副作用”处理。这比看到陌生工具就乐观重试更安全。[Hermes Tool Result Classification](https://github.com/NousResearch/hermes-agent/blob/63279301bcbdc185c1b07b98a9312eb0c862f26d/agent/tool_result_classification.py)

OpenCode 和 Codex 都保存工具或命令的运行状态，例如 `pending/running/completed/error` 或 `inProgress/completed/failed/declined`。这些字段能恢复界面和 Runtime，却不能单独证明支付、邮件或 Shell 副作用只发生一次。[OpenCode Tool State](https://github.com/anomalyco/opencode/blob/d2efd81fb3e153a51165b8589c4658107002817e/packages/schema/src/session-message.ts)、[Codex Command Status](https://github.com/openai/codex/blob/6d7f6dcd2285de70a3892d4f05b2a8ff44aa3350/codex-rs/app-server-protocol/schema/typescript/v2/CommandExecutionStatus.ts)

LangGraph 的 Pending Writes 可以在恢复失败节点时避免重跑同一 Superstep 中已经完成的节点。外部 Tool 能否安全重试，仍要看 Tool 或下游系统提供的幂等和对账能力。[LangGraph Checkpoint](https://github.com/langchain-ai/langgraph/blob/11738d83db4320bb191804342b5c76ae7eca54a0/libs/checkpoint/README.md)

## 8. 自己制造一次崩溃

完整一体化参考实现是 [`lesson_06_tool_reliability.py`](../examples/lesson_06_tool_reliability.py)。本章最新、最小的故障验证在[阶段一～二综合实践第 4～5 关](../exercises/phase-1-capstone/README.md#第四关ledger-与幂等)。

先运行完整综合检查：

```bash
python -B exercises/phase-1-capstone/starter.py --checkpoint-5
```

预期最后依次出现：

```text
checkpoint 4A passed
checkpoint 4B passed
checkpoint 4C passed
checkpoint 4D passed
checkpoint 5A passed
checkpoint 5B passed
checkpoint 5C passed
checkpoint 5D passed
checkpoint 5E passed
```

这五个恢复检查会亲手制造并验证：文件已经改变但 Ledger 停在 `running`、重启追加 `unknown`、补写 Tool Result、不追加新 User、对账后完成旧 Turn。

状态落盘的前置约束、三元标识体系（Tool Call / Execution / Idempotency）、孤立调用配对与 `unknown` 状态对账，构成了工具可靠性的核心闭环，必须在测试用例中严格验证。UUID 生成、SHA-256 规范化序列化与本地 Mock Client 等基础胶水代码，可在掌握机制后直接复用通用模块。面对支付、邮件等具有真实外部副作用的系统，必须依赖目标系统原生提供的幂等键协议与沙箱验收环境，切忌用内存假实现推导生产可用性。

下一课把时间倒回 Tool 执行之前：即使恢复和记账都正确，用户点了“允许”也不代表命令已经安全。[Agent Sandbox——审批、权限与执行边界](07-Agent沙盒.md)会继续区分 Tool Policy、Approval、Permission、Sandbox 与 Elevated。
