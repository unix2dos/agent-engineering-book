# 第 6 课：Tool Reliability——幂等、Ledger 与故障恢复

假设 Agent 已经发出退款请求，支付平台也处理成功了。它正准备保存回执，进程却崩溃了。

重启后，本地没有成功记录。直接再退一次，客户可能收到双倍退款；当成没发生，又可能漏掉已经完成的动作。钱没失忆，Agent 失忆了。

把场景缩小：任务要求把 `answer.txt` 写成 `done`。文件已经写好，程序却在保存 Tool Result 前中断。模型只看见一张没有回执的工具申请，无法知道工具没执行，还是执行后丢了消息。

```text
failed   已经确认执行失败
unknown  无法确认副作用是否发生
```

这次要解决的，就是怎样保留执行证据、恢复对话，并避免把一项动作做两遍。

## 1. 先记下“准备执行”，再改变外部世界

Transcript 保存用户、模型和工具之间的消息，供对话继续。程序还需要一份执行账本，记录工具何时获准、何时开始、最后得到什么结果。这份账本叫 **Tool Execution Ledger**，后面简称 Ledger。

同一次写文件请求，正常顺序是：

```text
保存 Assistant Tool Call
→ 用户拒绝：记 rejected，停止
→ 用户批准：记 approved
→ 记 running，并确认落盘
→ 执行 write_file
→ 把终态与 result 一起保存
→ 写回 Tool Result Message
→ 模型给出最终回答
```

`running` 必须先于文件变化。否则文件已经写了，磁盘却还显示“未开始”，恢复程序就可能误判并重做。

终态和结果也必须一起保存。例如：

```json
{
  "execution_id": "exec_1",
  "tool_call_id": "call_1",
  "status": "succeeded",
  "result": {"path": "answer.txt", "bytes_written": 4}
}
```

这是省略参数指纹等字段的记录示例。`status` 告诉程序执行到了哪里，`result` 提供能够重新交给模型的结果。不能先保存 succeeded，稍后才保存结果，否则中断后会出现“账上说成功，却拿不出回执”。

同一条记录表达两者一起提交的要求；实际持久化还要处理半条记录、写入失败和落盘确认，不能仅凭文件扩展名判断可靠性。

账本与对话可以存进同一份 JSONL，也可以分别保存。组装模型输入时，读取需要的对话和摘要；内部的 approved、running 和重试流水不必全部交给模型。

## 2. 重启后，先补回执

恢复时先查看每次执行的最后状态，再找只有申请、没有 Tool Result 的调用。

旧进程留下的 running，只能追加为 unknown。工具可能还没开始，也可能已经做完，恢复程序不能替过去下注。原 running 记录保留，让人能看清状态怎样变化。

接下来按账本决定怎样补回执：

| 已有证据 | 恢复动作 |
| --- | --- |
| 用户拒绝 | 补回拒绝结果 |
| 已有 succeeded / failed 和 result | 重放保存的结果，不再执行工具 |
| 状态是 unknown | 返回“不确定”，不自动执行 |
| 账本缺失、参数不匹配、终态缺少结果 | 停止恢复，检查记录 |

下面只展示已经核对调用身份和参数后的“取回执”逻辑：

```python
def replay_result(state):
    status = state["status"]
    if status == "rejected":
        return {"status": "rejected"}
    if status == "unknown":
        return {"status": "unknown"}
    if status in {"succeeded", "failed"}:
        if "result" not in state:
            raise RuntimeError("终态存在，但结果缺失")
        return state["result"]
    raise RuntimeError("这个状态还不能生成回执")

saved = {
    "status": "succeeded",
    "result": {"path": "answer.txt", "bytes_written": 4},
}
print(replay_result(saved))
print(replay_result({"status": "unknown"}))
```

输出为：

```text
{'path': 'answer.txt', 'bytes_written': 4}
{'status': 'unknown'}
```

这段代码没有调用 `write_file`。它取出已有证据，而不是通过再写一次文件来“补一个成功”。

把结果写成 `role=tool` 消息，配上原来的 `tool_call_id` 后，对话恢复到：

```text
User → Assistant Tool Call → Tool Result
```

下一位该说话的是模型。此时不能先插入一个新用户请求，应继续原来的 Turn，直到模型生成最终回答。

核验版本的 OpenClaw 也会检查未完成 Turn 中的工具调用和匹配结果，以及潜在副作用。缺少最终回答，不能成为重复执行已完成工具的理由。[1]

## 3. 三个编号，分别在追踪什么？

一次工具申请、一次执行尝试、一个需要防重的逻辑动作，是三件事：

| 编号 | 用来回答什么 |
| --- | --- |
| tool_call_id | 这条结果在回答模型的哪次申请？ |
| execution_id | 这是哪一次真实执行尝试？ |
| idempotency_key | 多个请求是否要求完成同一个逻辑动作？ |

假设同一逻辑动作允许安全重试，两次尝试可以这样记录：

```text
                 第一次          第二次
tool_call_id     call_1          call_1
execution_id     exec_1          exec_2
idempotency_key  write:call_1     write:call_1
```

这里的幂等键是教学用的生成方式，实际项目应按业务动作定义。模型两次独立提出相同参数，不一定是在要求同一件事；不能只因参数一样就合并两次调用。

参数 Hash 则用于检查内容有没有变化。将参数按固定方式序列化后计算指纹，可以发现：

```text
同一个幂等键，相同参数 → 可能是同一动作的重复请求
同一个幂等键，不同参数 → 身份冲突，停止
```

指纹不负责防重。真正接收动作的执行器或下游系统必须识别幂等键。给任意 Shell 命令贴一个 Key 没用：`echo sent >> audit.log` 不会读取它，执行两次仍会追加两行。

## 4. 两个 Worker 同时来了，谁能执行？

“先查有没有，再决定是否插入”挡不住并发。两个 Worker 都可能查到“没有”，随后一起开始执行。

判断应该交给真正写入时的唯一约束。下面用内存中的 SQLite 演示：同一个幂等键尝试插入两次，只有第一次插入一行。

```python
import sqlite3

db = sqlite3.connect(":memory:")
db.execute("""
    CREATE TABLE operations (
        op_key TEXT PRIMARY KEY,
        args_hash TEXT NOT NULL
    )
""")
sql = """
    INSERT INTO operations VALUES (?, ?)
    ON CONFLICT(op_key) DO NOTHING
"""

for attempt in range(2):
    with db:
        result = db.execute(sql, ("write:call_1", "hash_A"))
    print(result.rowcount)

db.close()
```

输出为：

```text
1
0
```

主键不允许出现第二条相同 Key 的记录。只有取得执行资格的一方才能开始动作；其他请求要读取已有参数和状态。参数不一致则报冲突，状态未知则按恢复规则处理，不能把第二次插入失败理解成“工具失败，再试一次”。

这段代码演示数据库里的资格裁决，不保证外部动作只发生一次。如果取得资格后进程崩溃，仍需要账本和恢复；如果支付平台已经处理请求，也仍需要它的幂等协议或权威回执。

## 5. 两张表，要一起更新

只追加事件，历史清楚，但每次恢复都要扫描。需要频繁查询时，可以同时维护“完整事件”和“当前状态”：

```text
execution_events          execution_state
exec_1: running           exec_1: unknown
exec_1: unknown
```

右边是从左边提前算出的当前答案。追加事件、更新当前状态，必须放在同一个数据库事务里；否则一边写着 unknown，另一边还停在 running。

下面故意让第二次写入失败。`NOT NULL` 禁止空值，写入 `None` 会触发约束错误：

```python
import sqlite3

db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE execution_events (status TEXT)")
db.execute("CREATE TABLE execution_state (status TEXT NOT NULL)")

try:
    with db:
        db.execute("INSERT INTO execution_events VALUES ('unknown')")
        db.execute("INSERT INTO execution_state VALUES (?)", (None,))
except sqlite3.IntegrityError:
    print("更新失败，事务已回滚")

print(db.execute("SELECT COUNT(*) FROM execution_events").fetchone()[0])
print(db.execute("SELECT COUNT(*) FROM execution_state").fetchone()[0])
db.close()
```

输出为：

```text
更新失败，事务已回滚
0
0
```

第一条事件也被撤回了，两张表没有留下互相矛盾的状态。这个例子只展示一起提交或回滚；真实表还需要执行编号、结果等字段。若当前状态表损坏，可按完整事件重新生成。

事务保护的只是这两次数据库写入。已经写出的文件、已经发出的邮件，不会因为这里回滚而自动复原。

内存数据库用于演示，关闭后不保留数据；恢复系统需要持久化存储。单进程、低频恢复时，JSONL 可以够用；需要频繁查询、事务和唯一约束时，再考虑 SQLite。WAL 能缓解本机读写等待，不能把 SQLite 变成多主机、多写者数据库。[2]

## 6. unknown 什么时候才能结束？

是否重试，要看工具的行为和已有证据。

纯读取通常可以重试；通用 Bash 可能删文件、发请求或追加日志，不能仅凭 unknown 自动重跑。即使是覆盖写文件，也要小心：崩溃后用户可能已经修改过它，再次覆盖会把新修改抹掉。

对“把文件写成 done”这个任务，可以先对账：

| 文件当前情况 | 处理 |
| --- | --- |
| 字节与原请求内容相同 | 不再写入，记录目标已满足 |
| 文件不存在或内容不同 | 保持 unknown，继续核对或交给用户 |

确认目标满足时，沿用原执行编号追加 succeeded，结果注明 `reconciled=true`。旧 unknown 保留。这个成功表示“要求的状态已经存在”，不证明旧进程写过几次，也不证明文件一定由它写成。

支付、发信等动作需要查询下游系统：用原幂等键查找属于这次请求的回执。没有证据时就保留不确定性，别用一次重试把缺少记录的问题变成重复执行的问题。

完整的恢复过程因此是：记住动作可能已经开始，保存可以重放的结果，补回工具消息，再让模型继续。账本负责留下证据，执行端负责防重，对账负责确认现实状态。一个 completed 字段承担不了这些工作。
