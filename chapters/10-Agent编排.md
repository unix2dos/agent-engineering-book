# 第 10 课：Agent Orchestration——Workflow、Routing 与长任务

假设 Agent 改完配置，回复“已经完成”。程序一查，主题改对了，端口却一起变了。如果它还能自行决定要不要检查，就同时兼任了施工队和验收员。

上一课已经有了判断产物的尺子。这一课把它接进执行过程：每轮修改后都由程序验收，失败才允许继续修复，达到上限就停止。哪些步骤由代码固定，哪里需要模型判断，怎样等待或转交任务，这些安排合起来叫 **Orchestration（编排）**。

## 1. 修改之后，程序必须自己验收

继续处理同一个任务：把 config.json 的主题改成 dark，其他字段不变。

```text
原始配置：{"theme":"light","port":3000}
第一轮后：{"theme":"dark","port":8080}
第二轮后：{"theme":"dark","port":3000}
```

第一轮失败，原因是端口被改了。第二轮恢复端口，才满足要求。程序应固定这条路线：

```text
Agent 修改文件
  -> 程序保存本轮产物并验收
  -> 通过：结束
  -> 未通过且还有预算：把失败原因交回 Agent，再修改
  -> 运行异常、评分异常或预算用完：停止并报告
```

固定步骤、条件和出口，就是这里的 **Workflow（工作流）**。模型仍可以判断怎样修；“修改后必须检查”由代码保证，不能只靠提示词提醒。程序也可能在没有修改时运行验收：一句“已经完成”同样要接受检查。

把模型运行状态和评分结果放到一起，决定下一步。下面先给定一次已取得的结果，只演示分支判断：

```python
agent_run = "completed"
grade = "failed"
remaining_attempts = 2

if agent_run != "completed":
    next_step = "inspect_run"
elif grade == "error":
    next_step = "inspect_grader"
elif grade == "passed":
    next_step = "completed"
elif remaining_attempts > 0:
    next_step = "needs_repair"
else:
    next_step = "stop"

print(next_step)
```

输出是 `needs_repair`，意思是进入修复。这里的评分结果只取 passed、failed、error；真正读文件和评分的动作，仍由上一课的评分器完成。完整工作流还检查模型请求的总预算。

配套实验已经把这条路线接进现有 Workspace Agent。模型使用固定剧本，文件工具、执行账本和评分器真实运行：第一轮写错端口，程序给出失败反馈；第二轮读取同一工作区并修正。两轮产物分别保留，修好以后也能看到最初错在哪里。这验证了控制流程，不证明真实模型一定能修好。

验收规则本身要受保护。模型可以指出测试与需求冲突，并提供证据；不能自己删掉断言，再宣布通过。运行发生异常时也不盲目开启下一轮，第 6 课里“副作用可能已经发生”的问题仍然存在。

### 用这条流程理解 LangChain 与 LangGraph

现有程序包含两层：里面是模型与工具来回交互的 Agent Loop，外面是“修改后验收、失败再修、预算用完停止”的工作流。先区分这两层，再看框架能省掉哪部分代码。

**LangChain 提供常见 Agent 循环的现成入口。** 你把模型、工具和指令交给它，不必每次重新组织工具调用与结果回传。在这个任务里，可以用它承担“让 Agent 修改配置”这一步；怎样读写文件、哪些路径允许访问，仍由应用定义。[4]

**LangGraph 让你直接组织任务的步骤和连接。** 把修改与验收分别作为节点，再按验收结果选择回到修改还是结束。“图”指的就是这些步骤及其连接，节点可以调用模型，也可以只是普通 Python 函数。[5]

对照同一个配置任务：

| 要做的事 | 现有 Python 实现 | 用 LangGraph 表达时 |
|---|---|---|
| 修改配置 | 调用已有 Agent Loop | 修改节点调用同一个 Loop，或调用 LangChain 的现成 Agent |
| 验收产物 | 调用配置评分器 | 验收节点继续调用同一个评分器 |
| 决定是否修复 | 循环里的条件判断 | 按运行、评分和预算状态选择下一条连接 |
| 记录进度 | 保存阶段、轮次与剩余额度 | 将这些字段放入图状态，需要恢复时配置合适的 Checkpointer |

采用 LangGraph 不要求把现有 Agent Loop 一起重写。它也能直接组织模型与工具循环；当前 LangChain 的 Agent 就建立在 LangGraph 之上。两者的差别是使用现成的 Agent 组织方式，还是更直接地控制步骤，不是“单 Agent 对多 Agent”。[4][5]

框架不会自动知道“端口必须保持 3000”，也不会替你决定可以修复几次。这些规则仍要写进评分器、分支和执行检查。配置了 Checkpointer，还需选择能满足恢复要求的存储，并处理副作用边界。

这个对照解释实现职责；配套工作流目前仍使用现有 Python 代码。若之后迁移到 LangGraph，应保留相同输入、评分器和停止规则重跑，才能判断两种实现是否符合相同要求。当前这条短流程已经能用普通代码表达，理解框架不要求立刻替换它。

## 2. 先选处理分支，再决定是否需要另一个 Agent

用户也可能只是要求“解释配置”。这时进入读取分支就够了，没有理由开放写入。按请求选择处理分支、工具或模型，叫 **Routing（路由）**。规则明确时可以由普通代码选；需要理解自然语言时可以让模型提出选择，但权限仍由程序检查。

路由选错不该变成越权。用户只要求解释，模型却申请写文件，执行器仍应拒绝。隐藏写工具也不够：若另一个工具允许任意 Shell 命令，写入可能从那里发生。权限与沙盒的完整边界见第 7 课。

任务变复杂以后，可以让专门的 Agent 参与，但先想清楚交出去的是一项子工作，还是后续处理权：

| 安排 | 谁负责接着推进 |
|---|---|
| 主 Agent 请子 Agent 分析错误，拿回建议 | 主 Agent 继续组织任务，这是委派 |
| 接待 Agent 把后续配置修改交给编辑 Agent | 接手者继续处理，这是 Handoff（交接） |

交接不等于销毁原 Agent，也不意味着任务完成。以后可以交回；实现上也不一定是两个进程。LangChain 的官方示例既支持不同 Agent 之间转交，也支持一个 Agent 根据状态切换指令和工具配置。[1]

交接时至少要安排当前处理者和必要资料。例如，交给编辑 Agent 的信息可以是“修改 config.json 的主题，保留端口；当前产物误改了端口”。程序要把这些资料放进接手者的输入，而不是只改一个 active_agent 字段。

历史很长时可以整理交接摘要；历史很短时可以直接传递相关消息。交接回答“谁接着做”，压缩回答“怎样缩短历史”，两者可以配合但不互相依赖。通过工具调用表达交接时，消息仍须保留完整的调用与结果配对。[1]

交接文本也不是授权。“之前已经批准”应当有可核验的审批依据，并且仍覆盖当前文件和操作。真正有效的批准可以沿用，不必因换了 Agent 就重复询问；参数变化、授权失效或接手者不在授权范围内，则不能照搬。

这个配置修改任务用一个 Agent 加固定验收已经能说明主线。只有职责、上下文或独立工作量确实需要拆分时，再增加协作者。

## 3. 并行前，先确认谁必须等谁

“分析错误、修改代码、验证修改”通常有依赖，分给三个 Agent 也不能让后一步提前拿到结果。测试旧版本可以与分析并行；验收新版本，则必须使用已经完成的那份修改。

真正适合并行的是相互独立的工作，例如检查三个互不依赖的模块。可用独立 worktree 隔离代码修改，并在报告中记录测试版本。worktree 不隔离数据库、端口或外部服务；共享的运行环境也需要安排。

结果回来后，主任务还要收集和合并。各自通过不等于组合后通过：一个修改接口字段，另一个新增按旧字段读取的功能，可能没有文本冲突，却会在组合后出错。因此最终验收必须针对合并后的版本。

主任务的记录不能只有一句“已经派出去了”：

```text
子任务 A：已完成，结果位置……
子任务 B：已完成，结果位置……
子任务 C：最后记录为运行中，下游任务编号 job_C
下一步：收齐结果后合并并验收
```

子任务的 Checkpoint 保存自己做到哪里；主任务的 Checkpoint 保存整体分工、收集进度和结果位置。它们可以存在同一个数据库，不必每个 Agent 各建一套存储。

恢复时，A、B 的结果直接复用。C 则按原任务编号查询：已完成就取回结果，仍在运行就等待，无法确认则停止自动推进。下面只处理这三种状态：

```python
def choose_next_step(statuses):
    if not statuses:
        raise ValueError("子任务列表不能为空")
    for status in statuses:
        if status not in {"succeeded", "running", "unknown"}:
            raise ValueError("这个短例不处理该状态")
    if "unknown" in statuses:
        return "reconcile"
    if "running" in statuses:
        return "wait"
    return "merge_and_validate"

print(choose_next_step(["running", "unknown"]))
print(choose_next_step(["succeeded", "succeeded"]))
```

输出依次是 `reconcile` 和 `merge_and_validate`：先核对未知结果；结果收齐以后才进入合并验收。`in` 检查列表里是否有这个值，`return` 返回决定并结束函数。这段代码本身没有轮询、合并或执行子任务。明确失败的子任务还需要相应的失败处理分支，不能归入“全部成功”。

## 4. 等不到结果，不代表远端已经失败

把同一任务的测试换成远端构建后，服务可能先返回一个任务编号，稍后才给结果。程序应保存本地任务与远端编号的对应关系、当前阶段、接手者以及下次查询安排。当前请求可以结束，整个任务仍在等待。

轮询由程序安排间隔和等待上限，不需要让模型不断说“再等等”。一次查询超时，只说明没有取得这次查询结果；保留原编号继续核对，不能因此重新提交构建。

等待、取消和补偿也要分开：

| 动作 | 它实际改变什么 |
|---|---|
| 停止等待 | 本地不再继续等，远端未必停止 |
| 请求取消 | 要求远端停止，仍需确认它是否接受并完成取消 |
| 事后补偿 | 原操作已经完成，再执行另一项获授权的补救动作 |

例如，取消请求发出后，远端报告构建已成功，就应保留成功事实与取消请求记录，不能改写成“已取消”。若已经部署，回退是另一项操作，需要自己的权限和执行结果。不能用状态字段代替现实动作。

保存进度也不自动解决重复副作用。LangGraph 的持久化说明把 Checkpoint 用于保存线程内的图状态；恢复设计仍要结合执行边界。[2] 对已经成功的操作复用回执，对结果未知的操作沿用第 6 课的核对规则。

配套恢复演示用独立进程保存和读取状态，下游结果由预设记录模拟。它验证了收集决策，没有启动真实后台服务，也没有实现远端取消。

## 5. 换处理者和重启，都不能给预算充值

一次任务允许的模型请求总数，要由主任务控制。A 用掉两次再交给 B，B 应拿到剩余额度；若每次换人都重置上限，两个 Agent 来回交接就可能一直运行。

下面只演示共享计数，不调用真实模型，也省略交接许可和上下文组装：

```python
state = {"remaining_calls": 2}

for agent in ["reader", "editor", "reader"]:
    state["active_agent"] = agent
    if state["remaining_calls"] == 0:
        print("停止：预算用完")
        break
    state["remaining_calls"] -= 1
    print(agent, "获准请求，剩余", state["remaining_calls"])
```

输出为：

```text
reader 获准请求，剩余 1
editor 获准请求，剩余 0
停止：预算用完
```

预算若定义为请求尝试次数，失败的请求也消耗一次；SDK 自动重试是否包含在计数内，也要说清。剩余额度应和任务状态一起保存，重启不能回到初始额度。扣减与发起请求之间仍有故障窗口；单进程计数不等于并发原子扣减，单次文件替换也不证明断电安全。

本章的配置实验同时限制总修改轮数和模型请求数。默认最多修改三轮，共用九次请求额度；同一轮还保留现有 Agent Loop 的四次请求上限。故意让三轮都改错，程序停止为 attempt_limit。把总请求预算缩到五次，第二轮文件虽然改对，却来不及取得最终回答，结果是 model_budget_exhausted，不是 completed。

到这里，模型负责提出动作和修复办法，程序负责验收、分工、等待与停止。当前综合实践已经接通配置修改工作流；交接和子任务恢复仍是独立模拟，尚未组成后台多 Agent 系统。下一课再处理多个真实任务同时到来时的队列、隔离、限流和部署问题。
