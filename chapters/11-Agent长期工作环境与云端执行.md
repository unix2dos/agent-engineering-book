# 第 11 课：Agent Runtime——持久状态与云端执行

Grok Bot 给 Agent 配了一台云电脑；Amp 的 Orbs 让开发任务在合上笔记本后继续运行。看到这些变化，很容易得出一个判断：以后 Agent 都要搬到云上了。

继续看 Amp 的文档，却会看到 Runner：可以从网页发起任务，让自己的电脑或服务器执行。云端环境与自有机器同时出现在一个产品里。这让我把问题改得更具体了一点：这些产品正在解除哪些依赖，又保留了哪些依赖？

本文沿这些产品的运行方式，检查会话、文件和执行进程分别怎样保留，再用一个故障实验说明恢复时需要核对什么。

## 1. Cloud Execution：客户端与执行进程

Grok Bot 的官方介绍强调长期保留的 Bot：有职责、记忆和上下文，能在云电脑上使用浏览器、文件与终端。关闭本地应用或笔记本，不会停止云端正在处理的工作。[1]

Amp 把开发任务放进 Orb。每个 Orb 线程获得独立环境，可以安装依赖、运行应用和测试。空闲后环境会休眠，再次发消息时唤醒，并保留工作现场。并行任务因此可以拥有各自的目录、端口和依赖，不再争用同一台笔记本的资源。[2]

它们首先解决的是设备依赖。以前在终端里运行一个 Agent，关掉终端可能连执行程序也一起结束；现在，手机和网页可以只是发送任务、查看结果的入口，真正干活的程序在另一台机器上。

这已经有实际价值。测试还在跑时，人可以离开；几个独立任务也可以同时工作。不过，关闭客户端仍能运行，只回答了客户端退出后的情况。如果执行程序自己崩溃，或者承载它的机器没了，还需要另一组能力。

**任务比界面活得久，和任务能从故障中恢复，是两个需要分别验证的承诺。**

## 2. Persistence：会话状态、工作区与长期记忆

“Agent 有自己的电脑”是一种容易理解的产品描述，具体归属却值得细看。Grok Bot 当前按账号共享云电脑：多个 Bot 共用文件和浏览器登录状态，每个 Bot 有自己的操作屏幕。屏幕之间并不构成独立的安全边界。[3]

与前面每个 Orb 线程的独立环境相比，这反映出不同的工作组织方式。我的理解是，Grok Bot 更强调长期角色之间复用资料与登录状态；Amp Orbs 更强调开发任务之间分开环境。这两种设计不能仅凭“都在云上”归成同一种方案。

讨论持久化时，也要说明保存的对象。以修复一个程序为例：

| 保存的东西 | 下次继续时有什么用 |
| --- | --- |
| 会话历史与任务进度 | 知道用户要求什么、上次做到哪里 |
| 工作区文件与产物 | 接着处理已修改的代码，读取测试报告 |
| 跨任务记忆 | 复用已经确认的项目约定和工作经验 |
| 临时进程与连接 | 继续某个正在运行的服务；能否恢复取决于环境能力 |

这些对象的寿命可以不同。保存了“测试通过”的一句话，测试报告未必还在；恢复了代码目录，原来的数据库连接也可能早就断了。

OpenAI 的 Sandbox Agents 文档就明确区分了运行状态 `RunState`、沙箱会话状态和工作区快照：分别用于接续运行控制、恢复环境连接，以及用保存的文件创建工作区。该能力目前处于 Beta，具体恢复行为还要看提供环境的后端。[4]

所以，“有持久化”之后还有一个问题：它承诺保住哪部分东西，覆盖哪一种故障？

## 3. Recovery：回执丢失与文件对账

为了看清这个问题，配套实验复用了已有的文件工具与执行账本。它不调用模型，而是给出一条固定请求：把配置中的主题改成 dark，端口保留 3000。

程序先记下工具准备执行，再修改文件。就在修改完成、成功回执尚未保存的位置，用 `os._exit(23)` 让执行进程退出。父进程确认它已经结束，然后启动另一个进程读取同一目录和账本。故障是主动注入的，文件写入与进程退出真实发生。

第一次，配置已经符合原请求。第二次，在启动恢复进程之前，模拟有人把端口改成了 8081。实际输出如下：

```text
文件符合原请求：进程退出码 23；running -> unknown -> succeeded；恢复未改写文件
文件被人修改：进程退出码 23；running -> unknown -> unknown；恢复未改写文件
```

`running` 是中断前留下的状态；`unknown` 表示当前还不知道那次动作的结果。新进程先把这份不确定性记下来，再检查文件。

第一种情况下，文件内容满足请求，可以记录“目标已满足”并补回结果。第二种情况下，文件已经不同，恢复逻辑保留 unknown，把未能确认的结果交回调用方。它没有用旧内容覆盖端口 8081。

这里用到的 **Ledger（执行账本）**，记录的是调用身份、参数和执行结果。它帮助恢复程序核对已经发生的动作。若把“没收到成功回执”直接当成“还没执行”，重跑一次就可能覆盖后来的修改。

这个实验也有清楚的边界：旧执行者已退出，只有一个恢复进程，文件仍在同一块可访问的磁盘上。它没有验证断电、容器丢失、并发接管或厂商服务的恢复质量。内容匹配只能说明当前目标满足，不能证明历史动作是谁做的、做了几次；发送邮件之类的操作还需要查询对应服务的结果。

脚本还检查了重复恢复不会重复补回执，并核对恢复前后的文件内容、文件标识和修改时间。运行入口见文末配套实践。

## 4. Harness 与 Sandbox：运行控制和执行环境

上面的实验保留了工作目录。如果旧机器连同目录一起消失，只有聊天记录，就接不回尚未保存的代码。要让执行机器可以更换，必须先安排哪些状态保留在机器之外，哪些能从可靠来源重建。

Anthropic 在 Managed Agents 的工程文章中介绍了这样的拆分：Session 保存事件，Harness 组织模型与工具循环，Sandbox 执行代码和文件操作。它将会话日志与运行程序分离，让 Harness 故障后可以重新读取日志接续；执行环境也通过工具接口访问。这是该团队公开描述的架构，不能直接当作所有产品的内部实现。[5]

Harness 可以理解成调用模型、接收工具申请、安排执行和处理结果的程序。Sandbox 则是工具实际运行的受限环境。两者拆开后，程序能够选择把动作发到哪里，并分别处理控制程序和执行环境的故障。

OpenAI 当前的 Agents API 也提供了类似的部署选择：由 OpenAI 运行 Harness，环境可以使用官方托管沙箱，也可以接到客户的笔记本、容器或远端机器。只调用某些外部工具的任务，还可以不配置自己的执行环境。[6]

这使“云端管理任务，本地或自有环境执行工具”成为一个具体的接口选择。但选择自托管环境时，环境的启动、连接、关闭以及文件保存，仍有需要应用方承担的责任。[7]

换机器时，至少要检查代码版本、未提交修改、依赖、权限与正在运行的远端任务。一个构建已经提交，恢复程序应按原编号查进度；一个登录状态已经失效，就需要重新建立访问条件。把旧记录送给新进程，并不会自动完成这些工作。

过去按 Model、Harness、Tool、Environment 划分职责，主要帮助我们找到谁负责什么。走到这里，还要追问：某一部分退出以后，其余部分能否保留足够的证据，继续承担原来的任务？部署架构正是在回答这个问题。

## 5. 部署选择：本地、自托管与云端

Amp 的 Runner 文档给出了直接例子：在自己的机器上启动 Runner，就能接收从网页创建的任务。文档同时明确，新功能优先进入 Orbs，因为标准化、隔离的环境更容易开发和支持。[8]

这两个选择可以同时成立。托管环境替用户处理了一部分启动、隔离与资源管理；执行放在自己的机器上，则可以利用那里已经存在的文件和运行条件。哪边省事，要回到任务。

代码能从仓库获取、依赖可以自动安装、测试需要并行运行时，我会更倾向托管云环境。若工作离不开本地 Obsidian 文件、桌面应用、USB 设备，或者企业内网资源，把所有东西迁过去可能比把执行留在原处更麻烦。即使数据已经在云上，也可能在客户自己的网络里，而非 Agent 厂商的网络里。

这就是数据与环境对执行位置的牵引：文件规模、访问权限、同步成本、延迟，都影响选择。模型通过云端 API 推理，也不要求读文件和跑命令一定发生在同一家云里。

我更看好标准化后台任务扩大采用托管环境的方向。它让用户离开设备后仍能交付工作，也给独立并行任务提供清楚的资源边界。不过，只有把部署准备、凭据接入、运行费用和验收成本一起算进去，才能判断一次迁移是否值得。若这些成本持续抵消收益，就应收窄云端执行的适用范围。

## 6. 趋势判断：产品承诺与验证依据

再遇到“自主工作”“长期记忆”“可恢复”之类的产品说明，可以先把承诺改写成一个具体场景：我关闭什么，它仍然继续？我丢掉什么，它能够恢复？恢复以后，凭什么判断原来的动作已经完成？

随后去找对应证据。支持跨设备查看，说明交互入口可以切换；说明文档里的恢复流程，给出了产品契约；在指定位置注入故障并核对产物，才开始验证那个位置的实际行为。几种证据能回答的问题不同。

我对这轮变化的判断是：更多任务会获得独立于用户界面的持续生命周期，托管云将承接其中适合标准环境的部分。执行位置会继续受到数据和工具的约束。真正值得关注的，是产品怎样保存任务、安排执行、处理不确定结果，并留下能够验收的产物。

下一次看到“电脑关了，它还在工作”，我会接着查它的恢复文档：旧执行者退出以后，谁接手，拿什么接手，又怎样知道哪些动作不能重做。
